系统可靠性 · 结构化知识点清单

一、知识点名称

系统可靠性（System Reliability）

二、核心定义与结论

基础概念辨析

可靠性 — 在规定时间、规定条件下完成规定功能的能力（三个"规定"是关键词）

可用性 — 系统处于可运行状态的时间占比，受可靠性和可维护性共同影响

两者区别：可靠性关注"有没有出故障"，可用性关注"能用的时间比例"

四大度量指标

```

MTTF（平均失效等待时间）= 1/λ

→ 从开机到第一次坏掉的平均时间

MTTR（平均故障修复时间）= 1/μ

→ 坏掉之后修好需要的平均时间

MTBF（平均失效间隔时间）= MTTF + MTTR

→ 两次故障之间的平均间隔

可用性 = MTTF / (MTTF + MTTR) × 100%

可靠度 R(t) = 在规定时间内无故障运行的概率（0~1之间的数值）

```

时间轴理解：

```

开机 坏了 修好 又坏了

←── MTTF ──←MTTR→←── MTTF ───

|←────────── MTBF ──────────────→|

```

失效率函数 f(t) 的性质

  • f(0) = 0，系统刚启动时故障概率为 0
  • f(t) 随时间单调递增，趋近于 1
  • 取值范围在 0 到 1 之间
  • 所有系统最终都会失效

可靠性管理各阶段任务

阶段主要任务
需求分析阶段分析影响可靠性的因素、确定可靠性目标、确定验收标准、制定管理计划
测试阶段可靠性建模（依赖测试数据，需求阶段没有数据，建不了模型）

可靠性测试分类

广义可靠性测试 — 核心目的是评价可靠性，包含定义操作剖面、收集数据、分析失效等完整流程

狭义可靠性测试 — 在给定操作剖面下，模拟真实使用场景，收集数据评价可靠性

操作剖面 — 描述用户使用系统的场景分布（如：80%查询、15%录入、5%删除）

N版本程序设计（NVP）

核心思想：同一需求让 N 个团队互不通气独立开发，通过多版本冗余实现容错

三个新增阶段（口诀：异审 → 异认 → 背靠背）：

  1. 相异成分规范评审 — 审查各团队对需求的理解是否足够"相异"
  2. 相异性确认 — 详细设计后确认各版本实现方案确实不同，防止公共故障
  3. 背对背测试 — 用相同输入并行跑所有版本，对比输出结果

单片机系统评价指标

单片机三要素：MTBF（可靠）+ 功耗（省电）+ 响应时间（快响应）

吞吐量属于服务器/网络/数据库系统的指标，不适用于单片机/嵌入式系统。

三、典型题型与解题要领

概念辨析题（如第15题）

  • 看到"规定时间 + 规定条件 + 规定功能"三个规定 → 锁定可靠性
  • 看到"无故障的概率" → 锁定可靠度 R(t)
  • 看到"时间占比/能用多久" → 锁定可用性

指标关系推导题（如第50题）

  • 先写出公式 MTBF = MTTF + MTTR
  • 代入题目给的条件（如 MTTR 极小）
  • 直接推导大小关系

阶段归属判断题（如第15题可靠性建模）

  • 需求阶段关键词：分析、确定、计划、标准
  • 测试阶段关键词：建模、数据、计算、评估
  • 建模需要数据，需求阶段没数据 → 建模不属于需求阶段

N版本程序设计题（如第51题）

  • 看到"相同"直接排除（NVP 的灵魂是"相异"）
  • 看到"面对面"直接排除（应该是"背对背"）

系统类型匹配题（如第22题）

  • 看到"吞吐量"就排除单片机/嵌入式选项

四、易错点与注意事项

可靠性 vs 可用性混淆

  • 可靠性强调"不出故障"，可用性强调"能用的时间比例"
  • 可用性受 MTTR 影响，可靠性不直接受维修速度影响

可靠度 vs 其他三个指标混淆

  • 故障率、MTTF、MTBF 都是时间或速率概念
  • 只有可靠度是概率（0~1 的数值），题目出现"概率"二字直接选可靠度

MTTF vs MTBF 的关系

  • MTBF = MTTF + MTTR，MTBF 永远 ≥ MTTF
  • 当 MTTR 极小时两者近似相等，不存在 MTTF > MTBF 的情况

f(t) 的单调性

  • f(t) 从 0 增大到 1，是单调递增，不是递减
  • "单调递减"是高频错误选项

广义可靠性测试的目的

  • 目的是"评价可靠性"，不是"发现缺陷提高质量"
  • 发现缺陷是过程，不是核心目标

可靠性建模的阶段归属

  • 建模依赖测试数据，只能在测试阶段完成
  • 需求阶段没有数据，无法建模

N版本程序设计的关键词

  • 三个阶段都带"相异"，不是"相同"
  • 测试方式是"背对背"，不是"面对面"

五、推荐复习顺序

第一步：建立概念框架

先搞清楚可靠性、可用性、可靠度三个核心概念的区别，这是所有题目的基础。

第二步：掌握四大指标和公式

背熟 MTTF、MTTR、MTBF、可用性四个公式，理解时间轴关系图，能做推导题。

第三步：理解可靠性管理阶段划分

重点记住"可靠性建模属于测试阶段"这一个易错点，其余需求阶段任务理解即可。

第四步：区分可靠性测试的广义/狭义

记住广义=评价，狭义=模拟收数据，操作剖面的概念顺带理解。

第五步：N版本程序设计

记住三个阶段名称和"相异"这个核心关键词，做题时用排除法。

第六步：补充了解

失效率函数 f(t) 的性质（超纲内容，了解即可）和单片机评价指标（记住排除吞吐量）。

子题1

参考答案：A

官方解析

本题考察的是系统可靠性及可靠性度量指标的基本概念。

可靠性强调在规定时间与条件下无故障完成规定功能；可用性强调“能用”的时间占比，它受可靠性与可维护性共同影响；常见度量中，可靠度R(t)刻画“在规定时间内无故障”的概率，是可靠性的核心概率度量。

问题 1：

A选项可靠性：指系统在规定时间、规定条件下完成规定功能的能力，符合题干定义，正确。

B选项可用性：指系统处于可运行状态的时间比例，通常与可靠性、可维修性（如MTTR）共同决定，不等同于题干所给定义。

C选项可理解性：指理解系统结构与代码/文档的难易程度，属于可维护性子特性之一，与题干无关。

D选项可测试性：指验证系统是否满足需求的难易程度，也属于可维护性子特性，与题干无关。

选择选项 A。

问题 2：

A选项失效率：单位时间内发生故障的速率（常记为λ），描述故障发生强度，不是“在规定时间内无故障的概率”。

B选项平均失效等待时间：从失效到开始维修的平均等待时长，偏向可维护性指标，不是无故障概率。

C选项平均失效间隔时间：两次相邻失效之间的平均时间（常与MTBF/MTTF相关），是时间指标而非概率。

D选项可靠度：系统在规定工作时间内无故障的概率，通常记为R(t)，与题干后半句完全一致，正确。

选择选项 D。

第2题（题号：50）

系统可靠性 难度：2

平均失效等待时间（mean time to failure，MTTF）和平均失效间隔时间（mcan time between failure，MTBF）是进行系统可靠性分析时的要指标，在失效率为常数和修复时间很短的情况下，（）。

子题1

参考答案：D

官方解析

本题考察的是系统可靠性分析中的四个核心指标，包括 MTTF、MTTR、MTBF 与系统可用性公式。

平均失效等待时间（MTTF）= 1/λ，λ 为失效率。

平均故障修复时间 (MTTR) = 1/μ，μ 为修复率。

平均失效间隔时间又称平均无故障时间(MTBF) = MTTR + MTTF。

系统可用性 = MTTF/(MTTR+MTTF)×100%

A选项 MTTF 远远小于 MTBF：在 MTTR 很小的情况下，MTBF≈MTTF，不存在“远远小于”的关系，错误。

B选项 MTTF 和 MTBF 无法计算：在失效率 λ 和修复率 μ 已知时，这两个指标是可以直接计算的，错误。

C选项 MTTF 远远大于 MTBF：与实际公式 MTBF = MTTF + MTTR 不符，错误。

D选项 MTTF 和 MTBF 几乎相等：公式 MTBF = MTTF + MTTR，当 MTTR 很小时，MTBF 与 MTTF 的差值可以忽略，因此几乎相等，正确。

选择选项 D。

📋 系统可靠性四大指标 · 精华笔记

🧠 顾名思义速记法（核心）

英文缩写中文拆解记忆白话意思
MTTF"等失效" — 等多久才坏从开机到第一次坏掉，平均要等多久
MTTR"等修好" — 坏了等多久修好坏掉之后，平均要花多久修好
MTBF"两次坏之间" — 两次故障之间隔多久从这次修好，到下次再坏，中间隔多久
可用性"能用的时间占比"系统真正能用的时间，占总时间的百分比

🔢 四个公式（必须背）

```

MTTF = 1 ÷ λ （λ 是失效率，坏得越快λ越大，能用时间越短）

MTTR = 1 ÷ μ （μ 是修复率，修得越快μ越大，修复时间越短）

MTBF = MTTF + MTTR （两次坏之间 = 能用时间 + 修复时间）

可用性 = MTTF ÷ (MTTF + MTTR) × 100%

```

🖼️ 字符时间轴图（帮助理解）

```

开机 坏了 修好了 又坏了

←——— MTTF ————————←— MTTR ———←——— MTTF ————————

| |

|←———————————————— MTBF ————————————————————————————|

```

> MTBF = MTTF + MTTR，就是"能用的时间"加上"修理的时间"

🎯 本题考点：为什么 MTTF ≈ MTBF？

题目条件：修复时间很短（MTTR 极小）

```

MTBF = MTTF + MTTR

当 MTTR ≈ 0 时：

MTBF ≈ MTTF + 0 ≈ MTTF

所以两者几乎相等 → 选 D

```

生活类比：

> 你的手机平均用 365 天会坏一次（MTTF=365天），

> 送去修只要 1 小时（MTTR极小），

> 那"两次坏之间的间隔"（MTBF）≈ 365天，

> 和 MTTF 几乎没区别。

选项说法为什么错
AMTTF 远小于 MTBFMTTR 很小时差值可忽略，不存在"远小于"
B无法计算λ 和 μ 已知就能算，说法错误
CMTTF 远大于 MTBFMTBF = MTTF + MTTR，MTBF 只会 ≥ MTTF，不可能更小

本题考察的是系统可用性（Availability） 的相关概念。

第5题（题号：51）

系统可靠性 难度：0

与通常软件开发过程不同的是，N版本程序设计增加了三个新的阶段，分别是（）。

子题1

参考答案：C

官方解析

本题考察的是N版本程序设计（N-Version Programming, NVP）中为实现容错与可靠性所引入的新开发阶段。

与普通软件开发过程相比，N版本设计通过多版本冗余提高容错能力，增加了三个特有阶段：

  1. 相异成分规范评审：多个开发小组在不了解其他组设计的前提下独立开发，确保设计“相异性”，通过独立理解同一份 SRS，并通过问题单反馈与协调。
  2. 相异性确认：在详细设计之后，通过分析或评估确保不同版本设计的实现机制、方法等具有相异性，从而降低公共故障的概率。
  3. 背对背测试（Back-to-Back Testing）：对各个版本使用相同的测试数据，并行执行，对比输出结果，检测是否存在一致性问题，从而发现潜在的软件缺陷。

因此，正确答案是：C. 相异成分规范评审、相异性确认和背对背测试。

第一阶段：相异成分规范评审

```

拆字理解：
```

> 🌰 举例：输入同一道数学题，3个版本答案分别是 5、5、7 → 第三个版本有问题。

第8题（题号：22）

系统可靠性 难度：0

在单片机系统性能与可靠性评价指标中，下列组合中哪一组指标最符合单片机系统常用的考量要素（）。

子题1

参考答案：D

官方解析

本题考察的是单片机（嵌入式系统）性能指标与可靠性指标的核心特征。

单片机系统不同于通用计算机系统，其关注点主要集中在：低功耗、可靠运行能力（如 MTBF）、实时响应能力（响应时间）。反之，吞吐量是服务器、网络系统、数据库系统中常见的性能指标，并非嵌入式系统的核心指标。

A选项吞吐量、MTBF、功耗：包含吞吐量，而吞吐量不属于单片机常用评价指标，因此该组合不正确。

B选项吞吐量、MTBF、响应时间：包含吞吐量，因此也不是单片机主要评价指标组合。

C选项吞吐量、功耗、响应时间：同样包含吞吐量，不符合嵌入式系统评价特性。

D选项MTBF、功耗、响应时间：均为单片机系统最主要的关注指标，因此该选项正确。

AI 记忆笔记

📝 系统可靠性 · 单片机评价指标记忆笔记

🧠 核心记忆口诀

> "单片机，不吞吐，要可靠、省电、快响应"

🔑 名词白话解释（零专业术语）

MTBF — "平均撑多久才坏"

> 全称：Mean Time Between Failures

> 白话：一台机器从正常运行到下一次出故障，平均能撑多少小时

> 顾名思义记忆：M（Mean均值）T（Time时间）B（Between两次之间）F（Failure坏掉）= 两次坏掉之间的平均时间

> 类比：你的手机平均用多久会死机一次，MTBF就是这个数字，越大越可靠

功耗 — "吃电量"

> 白话：机器运行时每秒消耗多少电

> 顾名思义：功（电功率）耗（消耗）= 消耗的电量

> 类比：手机待机一天耗20%电 vs 耗80%电，单片机装在设备里靠电池供电，当然越省电越好

响应时间 — "反应速度"

> 白话：你发出一个指令，机器多久给你反馈

> 顾名思义：响（响应回应）应（应答）时间 = 回应你需要的时间

> 类比：你按下电梯按钮，门多久打开，这就是响应时间

吞吐量 — "单位时间处理多少任务"

> 白话：一秒钟能处理多少请求/数据

> 顾名思义：吞（吞进来）吐（吐出去）量 = 进进出出处理的总量

> 类比：餐厅一小时能接待多少桌客人，这是餐厅（服务器）关心的，不是一个小家电（单片机）关心的

🎯 为什么单片机不用"吞吐量"？

```

通用服务器（淘宝后台） 单片机（空调控制板）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

每秒处理百万请求 ✅ 没有大量并发请求 ❌

不在乎耗多少电 ❌ 插电池运行，省电第一 ✅

坏了重启就行 ❌ 坏了可能出安全事故 ✅

响应慢点无所谓 ❌ 必须实时控制，慢了出问题 ✅

```
