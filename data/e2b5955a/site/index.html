📑 结构化要点清单

知识点 1：数据库基础常识（约束、安全、设计阶段）
  • 核心定义/结论：
  • 三大完整性约束：实体完整性（主键不为空/不重复）、参照完整性（外键必须存在）、用户定义完整性（产品经理定的业务规矩，如性别只能男女）。
  • 安全机制（存储过程）：封装在数据库里的“Java方法”，能更新数据且对外隐藏表结构。
  • 设计阶段：需求分析（纯聊天） $\rightarrow$ 概念设计（画E-R草图） $\rightarrow$ 逻辑设计（建表、拆表规范化、合表反规范化） $\rightarrow$ 物理设计（存硬盘、建索引）。
  • 派生属性：能通过其他字段算出来的属性（如年龄、总价），坚决不存库。
  • 典型题型与解题要领：
  • 题型：给场景问属于什么约束/阶段。
  • 要领：看到“反规范化”秒选逻辑设计；看到选项里同时有“出生日期”和“年龄”，立刻把“年龄”划掉。
  • 易错点与注意事项：
  • 视图（View）主要用于查询和隐藏结构，通常不能作为第三方更新数据的接口；触发器是被动的，不能主动调用。
知识点 2：SQL语法与关系代数（核心大头）
  • 核心定义/结论：
  • 操作对象：关系代数操作的输入和输出永远是集合（整张表），而不是单行（元组/记录）。
  • $\sigma$ (选择)：相当于 WHERE，按条件过滤行。
  • $\pi$ (投影)：相当于 SELECT，挑选出需要的列。
  • $\bowtie$ (自然连接)：相当于 INNER JOIN ... USING，自动找同名字段相等，并删掉重复的同名列。
  • HAVING 子句：必须和 GROUP BY（成团）绑定，用于过滤分组后的数据（没组你哈个啥？）。
  • 典型题型与解题要领：
  • 题型 1：算列数/行数。自然连接列数 = 表1列数 + 表2列数 - 同名列数。
  • 题型 2：代数转SQL。给两张表的字段从左到右打上数字序号（1,2,3...），自然连接自带“同名序号相等”的条件。
  • 题型 3：查询优化。核心原则：尽早执行选择（$\sigma$），把过滤条件下推，缩小中间结果。
  • 易错点与注意事项：
  • 单引号陷阱：代数式里的数字（如 2>7）代表第2列大于第7列。如果写成 2>'7'，就变成了第2列大于字符串常量'7'，绝对是错的！
知识点 3：函数依赖、候选码与属性闭包
  • 核心定义/结论：
  • 函数依赖 (A $\rightarrow$ B)：知道A就能唯一确定B（就像Map里通过Key找Value）。
  • 候选码：能顺藤摸瓜找出全表所有字段的“最小源头组合”。
  • 属性闭包：从某个字段出发，像滚雪球一样能卷进来的所有字段集合。
  • 典型题型与解题要领：
  • 题型：给一组依赖F，求候选码。
  • 要领（找源头法）：把依赖公式箭头右边出现过的字母全部划掉。剩下的从来没在右边出现过的字母，就是“入度为0”的源头，候选码必定包含它们！拿着它们去“滚雪球”验证即可。
  • 易错点与注意事项：
  • 候选码要求是“最小”的。如果 A 已经是候选码，那么 AB 包含冗余字段，只能叫超码，不能叫候选码。
知识点 4：数据库范式（1NF ~ BCNF）
  • 核心定义/结论：
  • 1NF：字段不可再分（原子性）。
  • 2NF：消除非主属性对码的部分依赖（不能只靠组合主键的一部分）。
  • 3NF：消除非主属性对码的传递依赖（拒绝第三者插足，A$\rightarrow$B$\rightarrow$C）。
  • BCNF：消除主属性对码的依赖（Boss老板也要守规矩）。
  • 典型题型与解题要领：
  • 题型：给一段描述，问属于第几范式。
  • 要领：条件反射连连看。看到“部分依赖”秒选 2NF；看到“传递依赖”秒选 3NF。
  • 易错点与注意事项：
  • 如果一张表只有一个字段做主键（单键），它天然不存在“部分依赖”，所以只要满足1NF，就必定直接满足2NF。
知识点 5：无损分解与保持函数依赖
  • 核心定义/结论：
  • 保持函数依赖：把大表拆成小表后，原题给的规矩（A$\rightarrow$B）在小表里还能完整装下。
  • 无损分解：拆开的小表用 JOIN 拼回去，数据行数一模一样，不产生多余的假数据。
  • 典型题型与解题要领：
  • 题型：判断拆表方案是否有损、是否保持依赖。
  • 要领（无损分解必杀公式）：
  1. 找两张小表的交集（公共列）。
  2. 找两张小表各自的差集（独有列）。
  3. 看交集能不能推导出其中一个差集。能推导就是无损，推不出就是有损。
  • 易错点与注意事项：
  • “无损”的本质是公共列在某一张小表里充当了“主键”，这样JOIN时才不会发生笛卡尔积爆炸。
知识点 6：Armstrong 公理系统
  • 核心定义/结论：
  • 自反律：大包小（X包含Y $\rightarrow$ X$\rightarrow$Y）。
  • 传递律：接力棒（X$\rightarrow$Y, Y$\rightarrow$Z $\rightarrow$ X$\rightarrow$Z）。
  • 合并规则：同因不同果，打包合并（X$\rightarrow$Y, X$\rightarrow$Z $\rightarrow$ X$\rightarrow$YZ）。
  • 分解规则：大果拆小果（X$\rightarrow$Y, Z是Y的一部分 $\rightarrow$ X$\rightarrow$Z）。
  • 典型题型与解题要领：
  • 题型：给一个字母推导公式，问叫什么规则。
  • 要领：顾名思义法。看到把结果拆开了就是分解，看到把结果拼一起了就是合并。代入具体的业务字段（如X=身份证，Y=完整用户信息，Z=姓名）去读一遍，瞬间秒懂。
  • 易错点与注意事项：
  • 千万不要当成离散数学题去死记硬背，用Java对象的包含关系（Entity与Field）去理解最快。

你好！针对这5道关于“特殊数据库系统”的真题，我为你梳理了结构化的知识点要点清单。结合你5年Java/SpringBoot的开发经验，我将这些理论知识与日常开发概念进行了映射，帮你用“顾名思义”的方法快速掌握。

知识点一：分布式数据库的“四大透明性” (⭐核心高频)

  • 核心定义/结论：

“透明”在计算机里指“看不见、不用管，系统替你干了”。按层级从高到低分为：

  1. 分片透明：不知道数据是怎么切块的（类似 ShardingSphere 分库分表）。
  2. 复制透明：不知道数据有几个备份、怎么同步的（类似 MySQL 主从复制）。
  3. 位置透明：不知道数据存放在哪个物理机房/IP地址（类似 Nacos 服务发现，只认名字不认IP）。
  4. 逻辑透明（局部映像透明）：不知道底层用的是什么数据库软件或方言（类似 Hibernate/JPA 屏蔽了底层SQL差异）。
  • 典型题型与解题要领：
  • 题型：概念“连连看”。题干给出一段描述，问属于哪种透明性。
  • 解题要领（找关键词）：
  • 看到“物理位置、存放站点” ➔ 选 位置透明
  • 看到“数据模型、操纵语言” ➔ 选 逻辑透明
  • 看到“划分、片段” ➔ 选 分片透明
  • 看到“副本、冗余、更新同步” ➔ 选 复制透明
  • 易错点与注意事项：
  • 别名陷阱：“逻辑透明”在考试中经常被称为“局部映像透明”，两者是同一个东西。

知识点二：分布式数据库的“模式结构” (⭐核心高频)

  • 核心定义/结论：

描述分布式数据库架构的分层设计：

  1. 全局外模式：给外部不同应用看的局部视图（类似 Java 中的 VO/DTO）。
  2. 全局概念模式：描述整体逻辑结构，感觉不到数据被拆分（类似 Java 中的完整 Entity 实体类）。
  3. 分片模式：定义如何将全局数据切分（类似分表规则配置）。
  4. 分布/分配模式：定义切好的数据块放在哪个物理节点上（类似多数据源 IP 配置）。
  • 典型题型与解题要领：
  • 题型：概念对应题。
  • 解题要领（找关键词）：
  • 看到“整体逻辑结构、如同没有分布一样” ➔ 选 全局概念模式
  • 看到“不同应用、用户视图” ➔ 选 全局外模式
  • 易错点与注意事项：
  • 极易混淆“全局外模式”和“全局概念模式”。记住：外模式是局部的（给外人看的），概念模式是全局完整的（自己脑子里的整体概念）。

知识点三：分布式事务的“两阶段提交 (2PC)”

  • 核心定义/结论：

为了保证分布式事务的原子性和一致性（要么全成功，要么全失败），分为两个阶段：

  1. 表决阶段（准备阶段 Prepare）：协调者问所有节点“能提交吗？”，节点记录日志并回复“同意/中止”。
  2. 执行阶段（提交阶段 Commit）：如果全同意，则统一提交；只要有一个中止，则统一回滚。
  • 典型题型与解题要领：
  • 题型：直接问两阶段提交包含哪两个阶段。
  • 解题要领：认准 “表决阶段、执行阶段”（或准备阶段、提交阶段）。
  • 易错点与注意事项：
  • 名称混淆陷阱：选项中常出现“扩展阶段、收缩阶段”，这是两阶段锁协议（2PL）的概念，用来管并发控制的，千万别和两阶段提交（2PC）搞混！

知识点四：数据仓库的“四大特点”

  • 核心定义/结论：

数据仓库（Data Warehouse）是为决策分析服务的，有四个核心特点：

  1. 面向主题：按业务分析主题（如销售、客户）组织数据。
  2. 集成性：数据来自不同系统，经过了统一清洗和格式转换（ETL）。
  3. 相对稳定性（非易失性）：数据一旦进入数仓，主要用于查询，很少修改和删除。
  4. 反映历史变化：保留了不同时间点的数据快照，用于趋势分析。
  • 典型题型与解题要领：
  • 题型：给出一段描述，问体现了数仓的哪个特点。
  • 解题要领（找关键词）：
  • 看到“长期保留、很少修改和删除” ➔ 选 相对稳定性
  • 看到“统一编码、消除不一致” ➔ 选 集成性
  • 易错点与注意事项：
  • 容易把“相对稳定性”和“反映历史变化”搞混。记住：不改不删 = 稳定；带时间戳/看趋势 = 历史。

知识点五：嵌入式与网络数据库 (EDBMS & NDB)

  • 核心定义/结论：
  • 嵌入式数据库 (EDBMS)：运行在小设备（PDA、车载）上。特点：轻量、支持实时处理、支持多线程并发、一般只提供本机服务接口。
  • 基于网络的数据库 (NDB)：数据在远端服务器。由客户端、通信协议、远程服务器组成。客户端小且可裁剪。
  • 基于文件的数据库：数据直接以文件形式存在本地磁盘，程序直接读写。
  • 典型题型与解题要领：
  • 题型：描述正误判断题（选不正确的）。
  • 解题要领：
  • 看到“EDBMS不支持多线程” ➔ 错（现代SQLite等都支持多线程）。
  • 看到“NDB直接对本地数据文件读写” ➔ 错（NDB数据在网络远端，本地读写的是文件数据库）。
  • 易错点与注意事项：
  • 不要用“设备性能差”的刻板印象去推断EDBMS不支持多线程；
  • 严格区分“网络库（异地恋，靠协议通信）”和“文件库（同居，直接读写本地磁盘）”。

为您将2013年11月系统架构真题中涉及的“数据库设计”相关知识点进行了系统归纳，形成以下结构化的要点清单，方便您高效复习与记忆：

知识点一：数据库转储（备份）方式

  • 知识点名称：数据库转储机制（状态与范围的组合）
  • 核心定义/结论：

数据库转储（备份）由“转储状态”和“转储范围”两个维度组合而成，共4种方式：

  1. 按转储状态（是否停机）：
  • 静态转储：转储期间禁止任何事务运行（相当于停机维护，数据一致性高，但可用性差）。
  • 动态转储：转储期间允许事务并发运行（相当于热备份，不停机，可用性高）。
  1. 按转储范围（备份多少）：
  • 全局转储（海量转储）：每次转储数据库的全部数据。
  • 增量转储：只转储自上次转储以来发生变化的数据。
  • 典型题型与解题要领：
  • 题型：题干给定特定的业务场景（如“有正在运行的事务”、“需要备份全部数据”），要求选择合适的转储方式。
  • 解题要领（找关键词秒杀）：
  • 看到“有正在运行的事务 / 允许并发 / 不停机” ➡️ 锁定 动态。
  • 看到“不允许存取修改 / 等待事务完成” ➡️ 锁定 静态。
  • 看到“全部数据 / 整个数据库” ➡️ 锁定 全局。
  • 看到“变化的数据 / 更新的部分” ➡️ 锁定 增量。
  • 易错点与注意事项：
  • 术语替换：考试中有时会将“全局转储”称为“海量转储”，两者是同义词，看到“海量”直接等同于“全部”即可。
  • 动态转储的代价：动态转储虽然不停机，但由于备份期间数据可能被修改，必须结合日志文件（Log）才能将数据库恢复到一致性状态。

知识点二：E-R图集成冲突与解决

  • 知识点名称：局部 E-R 图合并时的“三大冲突”
  • 核心定义/结论：

在将多个局部 E-R 图合并为全局 E-R 图时，常出现以下三种冲突：

  1. 命名冲突：名字没起好。包括“同名异义”（同名但代表不同概念）和“异名同义”（不同名但代表同一概念）。
  2. 属性冲突：内在特征打架。同一属性的数据类型、取值范围、单位不同（如一个是整数，一个是浮点数；一个是公斤，一个是斤）。
  3. 结构冲突：层级或长相打架。同一对象在不同图中抽象级别不同（如A图作为“实体”，B图作为“属性”），或者同一实体包含的属性个数/排列顺序不同。
  • 典型题型与解题要领：
  • 题型：给出两个部门对同一业务的不同设计，第一问判断属于哪种冲突，第二问选择如何消除该冲突。
  • 解题要领：
  • 判别冲突：只要看到“实体 vs 属性”的降维/升维差异，或者“属性数量不同”，直接选结构冲突。
  • 解决冲突：针对“实体 vs 属性”的结构冲突，核心口诀是“大包小，删实体，加属性”。即保留层级更高的实体，将层级较低的实体删除，并将其转化为高层级实体中的一个区分属性（如：删除“培训师”实体，在“员工”实体中增加“职称”属性）。
  • 易错点与注意事项：
  • 属性冲突 vs 结构冲突：极易混淆！“属性冲突”仅仅是同一个属性的类型/单位不同；而把一个概念当成实体还是当成属性，属于架构层级的变化，是“结构冲突”。
  • 实体冲突：选项中常出现“实体冲突”作为干扰项，标准数据库理论中没有这个分类，直接排除。

📑 数据库基本概念：结构化要点清单

1. 数据库三级模式（高频送分题）
  • 核心定义/结论：
  • 外模式（用户模式/子模式）：外部用户/程序员看到的局部视图。（👉 Java类比：VO / DTO，只给前端看部分字段）。
  • 概念模式（模式/逻辑模式）：全局表结构、数据类型、约束。（👉 Java类比：Entity 实体类，数据库全貌）。
  • 内模式（物理模式）：底层物理存储、索引、文件。（👉 Java类比：MySQL底层的 InnoDB 引擎、B+树、.ibd 文件）。
  • 典型题型与解题要领：
  • 题型：概念连连看（给一段描述，问属于什么模式）。
  • 要领（找关键词）：
  • 看到“局部、用户、视图、应用程序” ➡️ 选 外模式。
  • 看到“全局、整体、数据类型、完整性” ➡️ 选 概念模式。
  • 看到“物理、存储、磁盘、索引（如聚簇索引）” ➡️ 选 内模式。
  • 易错点与注意事项：
  • 选项中常出现“物理模式”或“逻辑模式”。记住：标准叫法是“内模式”和“概念模式”。如果题目里没有“概念模式”，选“逻辑模式”也对；但如果有“内模式”，千万别选“物理模式”（通常是凑数的干扰项）。
2. 数据库事务 ACID 特性
  • 核心定义/结论：
  • 原子性 (Atomicity)：不可分割，全有或全无。（👉 顾名思义：原子不可再分）。
  • 一致性 (Consistency)：执行前后规矩不变，总账要平。（👉 顾名思义：前后一致）。
  • 隔离性 (Isolation)：并发执行互不干扰。（👉 顾名思义：关在小黑屋各玩各的）。
  • 持久性 (Durability)：提交后落盘生根，停电不丢。（👉 顾名思义：永久保存）。
  • 典型题型与解题要领：
  • 题型：选出不属于事务特性的选项，或根据描述匹配特性。
  • 要领：死记四个字“原一隔持”。
  • 易错点与注意事项：
  • “并发性”、“可靠性”、“安全性” 都是用来形容整个数据库系统的，绝对不是单个事务的特性！看到直接排除。
3. 关系代数（笛卡尔积与自然连接）
  • 核心定义/结论：
  • 笛卡尔积 (×)：两张表无脑全排列组合。（👉 Java类比：双层 for 循环）。
  • 自然连接 (⨝)：两张表按同名列拼接，且自动去重。（👉 顾名思义：“自”动去重，“然”后拼接）。
  • 典型题型与解题要领：
  • 题型：计算连接后的元组数（行数）或属性列数（列数）。
  • 要领：
  • 求笛卡尔积的行数：表1行数 $\times$ 表2行数（乘法）。
  • 求自然连接的列数：表1列数 $+$ 表2列数 $-$ 重复的同名列数。
  • 易错点与注意事项：
  • 审题一定要看清是问“元组数（行）”还是“属性列数（列）”。
  • 区分“等值连接”和“自然连接”：等值连接不去重同名列，自然连接必须去重同名列。
4. 候选键与属性闭包
  • 核心定义/结论：
  • 函数依赖 (A → B)：知道A就能查出B。（👉 Java类比：getB(A) 方法）。
  • 候选键：能顺藤摸瓜找出全表所有字段，且没有多余字段的最小组合。（👉 Java类比：数据库主键）。
  • 闭包：从某个字段出发，能“滚雪球”找出的所有字段集合。
  • 典型题型与解题要领：
  • 题型：给定关系模式和依赖集，求候选键。
  • 要领（画图找源头法）：
  1. 在草稿纸上把 A → B 画成箭头图。
  2. 找“只有指出去的箭头，没有指进来的箭头”的字母（入度为0），它必定是候选键的一部分。
  3. 顺着它往下走，看能不能找齐所有字母。
  • 易错点与注意事项：
  • 候选键必须是“最小”的。如果 A 就能找齐所有人，那 AB 就不是候选键（因为 B 是多余的）。
5. 数据库范式
  • 核心定义/结论：
  • 1NF：列不可分（不能有集合/数组）。
  • 2NF：消除部分依赖（联合主键里，不能有字段只依赖一半的主键）。
  • 3NF：消除传递依赖（拒绝中间商，A->B->C）。
  • 4NF：消除多值依赖（一对多且毫无关系的属性，必须拆表）。
  • 典型题型与解题要领：
  • 题型：判断属于第几范式，或某范式消除了什么依赖。
  • 要领（口诀）：单主键=保底2NF；消部分=升2NF；消传递=升3NF；消多值=升4NF。
  • 易错点与注意事项：
  • 如果题目给出 A->B, B->C，说明存在传递依赖。既然存在，说明它还没有消除传递依赖，所以它绝对不是3NF，只能停在2NF。

本题考察的是关系代数表达式的等价变换与代价优化原则。

核心原则是：尽可能将选择（σ）下推到越接近数据源越好，尽可能避免先做笛卡儿积（×），优先使用连接（⋈），并减少中间结果规模。题干四式在语义上应等价；常见等价关系为：E1 与 E2 等价（选择下推到连接两端），E3 与 E4 等价（连接转化为对笛卡儿积的选择，并尽量下推选择）。在“严格按写出的运算顺序执行”的前提下，比较中间结果规模与操作类型，E2的执行代价最低。

A选项 E1：先做连接 R ⋈ S，再整体选择 σ{A2<2018 ∧ A4='95'}。先连接后选择会产生较大的中间结果，因为连接在未过滤前参与元组更多，随后再过滤，代价高于先选择再连接，所以不是最优。

B选项 E2：先对 R 与 S 分别执行选择 σ{A2<2018} 与 σ{A4='95'}，再做连接，然后投影。这是标准的“选择下推 + 再连接”策略，能显著缩小参与连接的关系规模，减少连接代价与中间结果，严格按序执行时查询效率最高，因此正确。

C选项 E3：先做笛卡儿积 R × S，再一次性做包含等值连接条件与选择条件的总选择，最后投影。笛卡儿积在未约束时会产生规模巨大的中间结果，随后再用σ过滤，代价通常最高，因此最差。

D选项 E4：先分别下推选择到 R 与 S，随后做笛卡儿积，再用 σ{R.A3=S.A3} 实现等值连接。相比 E3，已经做了部分优化（先选择），中间结果小于 E3；但仍然显式执行了笛卡儿积再过滤为连接，通常劣于直接连接的 E2，因此不是最优。

  • 看U2{B,D,E}：能装下原规矩 B→D 和 D→E 吗？能！B,D,E都在U2里。
  • 结论：原规矩全都在，保持了函数依赖。
  • 第二问：是无损连接吗？（⭐核心记忆公式）
  • 大白话公式：两表的“公共列”，必须是其中一张表的“主键”（能决定该表独有的其他列）。
  • 算交集（找公共列）：U1 和 U2 都有谁？是 B。
  • 算差集（找独有列）：U2 独有的是 {D, E}。
  • 查规矩：公共列 B，能决定 U2 的独有列 {D, E} 吗？
  • 根据刚才的顺藤摸瓜：B→D 且 D→E，所以 B→DE。成立！
  • 结论：公共列B是U2的“主键”，所以拼表时不会错乱，是无损连接。
  • 选A！

💡 第一部分：专业名词“顾名思义”大白话翻译

我们先用大白话把题目里的“天书”翻译成您日常开发中的概念，绝对不用专业名词解释专业名词：

  • 关系 R (Relation)
  • 顾名思义：就是一张“数据库表”。
  • 大白话：别管什么关系不关系，它就是一张MySQL里的Table。
  • 属性 U (Attribute)
  • 顾名思义：表里面属于它的“性质/字段”。
  • 大白话：就是表的“列名”。题目里的 U={A,B,C,D,E}，你就当成这张表有5个字段：字段A、字段B、字段C、字段D、字段E。
  • 函数依赖 F (Functional Dependency, 比如 A→B)
  • 顾名思义：像函数一样，给一个输入，就“必定依赖”出一个输出。
  • 大白话：就是“顺藤摸瓜的线索”。A→B 的意思是：只要我知道了字段A的值，我就能唯一确定字段B的值。
  • Java秒懂：就像 map.get(A) 一定能拿到 B。
  • 属性闭包 (Closure，符号是 $[X]^+_F$)
  • 顾名思义：“闭”=完结/全部，“包”=打包。把能顺藤摸瓜找到的所有字段“全部打包”在一起。
  • 大白话：“滚雪球”。给你一个初始字段（比如A），根据线索（F），看看你的雪球最大能滚多大，能把多少个字段卷进来。
  • Java秒懂：就像Maven的传递依赖。你只在pom.xml里引入了A，但A依赖B，B依赖C，最后Maven给你“打包”下载了A, B, C。这个{A,B,C}就是A的闭包！
  • 候选码 (Candidate Key)
  • 顾名思义：有资格“候选”当主键的“号码/字段”。
  • 大白话：“全村的希望”。它是最小的起始字段集合，只要有了它，就能顺藤摸瓜把表里所有字段（A,B,C,D,E）都找出来。

🚀 第二部分：解题必杀技 —— “找源头”作图法

这道题根本不需要死记硬背复杂的数学公式，我们用“画箭头找源头”的方法，10秒钟就能看破玄机！

1. 题目线索（依赖关系 F）翻译：
  • A→B ：有A就能找到B
  • D→C ：有D就能找到C
  • BC→E：必须同时有B和C，才能找到E
  • AC→B：必须同时有A和C，才能找到B
2. 字符图解（顺藤摸瓜图）：

我们把线索画成箭头，箭头指向谁，谁就是“小弟”（被推导出来的）。

```text

(源头1) A --------> B

|

v (B和C结合)

(源头2) D --------> C --------> E

```

3. 破题口诀：【找“入度为0”的节点】
  • 顾名思义：“入度”就是“射入的箭头数量”。入度为0，就是没有箭头指向它。
  • 大白话：没有箭头指向它，说明没有任何人能推导出它。它就是“老祖宗”（源头）。
  • 看图找源头：
  • A：没有箭头指向A。A是源头！
  • D：没有箭头指向D。D是源头！
  • B、C、E：都有箭头指向它们，它们都是小弟。
  • 结论：既然A和D谁也推导不出来，那么想找齐所有人，一开始的手里必须同时拥有 A 和 D。所以，候选码必定包含 AD！

解决子题2：求候选码（先做这题更简单）

根据我们上面的口诀，找没有箭头指向的字母。

说明 B, C, E 都能被别人找出来。

唯独 A 和 D 从来没出现在箭头右边！

所以 A 和 D 是源头，必须选！

答案直接秒选 A (AD)。

解决子题1：求属性闭包的等式成立的是？

题目问：下面哪个选项的“雪球”滚到最后，能等于 U（也就是包含A,B,C,D,E全部）？

既然我们刚才算出候选码是 AD，意思就是“只有AD能找齐所有人”。我们来验证一下 D选项 (AD)+ 的滚雪球过程：

  1. 初始雪球：手里有 {A, D}
  2. 用线索 A→B：手里有A，抓到了B。雪球变大：{A, D, B}
  3. 用线索 D→C：手里有D，抓到了C。雪球变大：{A, D, B, C}
  4. 用线索 BC→E：手里现在有B和C了，抓到了E。雪球变大：{A, D, B, C, E}
  5. 结果：找齐了！等于 U。

答案选 D。

在分布式数据库中有分片透明、复制透明、位置透明和逻辑透明等基本概念。其中，（）是指用户无需知道数据存放的物理位置。

子题1

参考答案：C

官方解析

本题考察的是分布式数据库的四种透明性的基本概念。

分布式数据库系统通常具备四种透明性：分片透明性、复制透明性、位置透明性和局部映像透明性（又称逻辑透明性），它们共同目的是让用户在使用数据时无需关心底层数据的组织与存储方式。

A选项 分片透明：指用户在进行数据操作时，不必关心数据是如何分片的，也无需了解分片位置，系统会自动定位到相应的数据片段并执行操作。它解决的是数据拆分结构的透明性，而不是位置问题，因此不符合题意。

B选项 逻辑透明：又称局部映像透明性，指用户不必关心各站点局部数据库使用的具体数据模型与操纵语言，系统会自动进行数据模型和操作语言的映射与转换。这是数据模型层面的抽象，不涉及物理位置，因此不符合题意。

C选项 位置透明：指用户不需要知道数据的物理存放位置，系统会自动定位到存储数据的站点并完成操作。当数据位置发生变化时（如从一个站点迁移到另一个站点），应用程序无需修改。这正是题干描述的含义，因此正确。

D选项 复制透明：指用户不必关心数据在不同节点的复制情况，系统会自动完成复制数据的更新与维护。它解决的是数据冗余副本的透明性，而非物理位置问题，因此不符合题意。

因此，本题选择 C。

🧠 “顾名思义”逐个击破（绝对不用专业词汇解释）

1. 位置透明 (本题答案 C)

  • 顾名思义：位置 = 在哪儿。位置透明 = 不用管数据放在哪儿。
  • 大白话解释：就像你用手机点外卖，你只管点“宫保鸡丁”，你不需要知道这盘菜是在北京厨房炒的还是上海厨房炒的（物理位置），外卖小哥（系统）会自动给你送来。
  • Java秒懂：就像微服务里的 Nacos 或 Eureka。你调服务只用写服务名（如 order-service），根本不用写对方的IP地址（物理位置）。
  • 做题找关键词：题干里看到 “物理位置”、“存放地点”、“站点” -> 秒选 位置透明。

2. 分片透明 (选项 A)

  • 顾名思义：分片 = 切成小块。分片透明 = 不用管数据是怎么切块的。
  • 大白话解释：一张100万人的大表，被切成了10个小表。你查询的时候，不需要自己去拼凑这10个小表，你只管查，系统会自动帮你把碎片拼好给你。
  • Java秒懂：就像用了 ShardingSphere 或 MyCat（分库分表中间件）。你代码里写的还是 select * from user，中间件会自动帮你去查 user01, user02。
  • 做题找关键词：题干里看到 “分片”、“怎么拆分的”、“分片条件” -> 秒选 分片透明。

3. 复制透明 (选项 D)

  • 顾名思义：复制 = 搞了几个备份。复制透明 = 不用管数据有几个备份，也不用管它们怎么同步。
  • 大白话解释：你存了一份文件，系统为了安全偷偷在别的电脑上也复制了3份。你修改文件时，只需要改一次，系统会自动把另外3份也改了，你完全不用操心。
  • Java秒懂：就像 MySQL 的 主从复制。你只管往数据库里写数据，至于数据怎么同步到从库（备份），你写代码的时候根本不用管。
  • 做题找关键词：题干里看到 “复制”、“副本”、“冗余”、“更新同步” -> 秒选 复制透明。

4. 逻辑透明 / 局部映像透明 (选项 B)

  • 顾名思义：逻辑 = 底层用的啥规矩/方言。逻辑透明 = 不用管底层具体用的是什么数据库软件。
  • 大白话解释：不管底层是存放在Excel里、TXT文档里，还是专业的数据库里，你用起来感觉都一样。系统帮你把你的命令翻译成了它们能听懂的“方言”。
  • Java秒懂：就像用了 Hibernate 或 JPA。你只管写 Java 对象操作，底层到底是 MySQL 还是 Oracle，你不用管，框架会自动帮你翻译成对应的 SQL 方言。
  • 做题找关键词：题干里看到 “数据模型”、“操纵语言”、“局部数据库” -> 秒选 逻辑透明。

  • 属性 (Attribute) = Java类里的一个字段 (Field)，比如 private String name;。
  • 局部E-R图合并 = 两个微服务要合并成一个单体，或者两个程序员写的实体类要合并到一起，发现两边设计得不一样，打架了。

考试只会考三种冲突，我们通过“看名字猜意思”来死死记住它们：

1. 命名冲突 (名字打架)

  • 顾名思义：纯粹是“名字”没起好，或者叫法不同。
  • 大白话解释：
  • 同名异义：都叫 id，张三指的是“身份证号”，李四指的是“工号”。
  • 异名同义：张三叫 telephone，李四叫 phone，其实都是电话。
  • Java代入：变量名起得不一样。

2. 属性冲突 (类型/单位打架)

  • 顾名思义：名字虽然一样，但“属性的内在特征”（类型、范围、单位）不一样。
  • 大白话解释：都叫“体重”，张三用的是“公斤(kg)”，李四用的是“斤”；或者张三用的是整数型 int，李四用的是浮点型 double。
  • Java代入：字段的数据类型不一样（Integer vs String）。

3. 结构冲突 (级别/长相打架) —— 🌟 本题考点！

  • 顾名思义：事物的“层级结构”或“整体长相”发生了变化。

官方解析

此题考察Armstrong 公理系统的相关概念。

设关系模式 R\<U，F\>，其中 U 为属性集，F 是 U 上的一组函数依赖，则有：

① A1自反律：若 Y⊆X⊆U，则 X→Y 为 F 所蕴含；

② A2增广律：若 X→Y为 F 所蕴含，且 Z⊆U，则 XZ→YZ 为 F 所蕴含；

③ A3传递律：若 X→Y，Y→Z 为 F 所蕴含，则 X→Z 为 F 所蕴含。

根据上面三条推理规则，又可推出下面三条推理规则：

④ 合并规则：若 X→Y，X→Z，则X→YZ 为 F 所蕴含；

⑤ 伪传递规则：若 X→Y，WY→Z，则 XW→Z 为 F 所蕴含；

⑥ 分解规则：若 X→Y，Z⊆Y，则 X→Z 为 F 所蕴含。

🧠 核心考点：六大规则的“顾名思义”记忆法

我们把这6个规则当成6个Java工具类方法，看名字就知道它在干嘛：

1. 自反律 (Reflexivity)

  • 顾名思义：自己反过来推导自己的一部分。
  • 公式：若 Y ⊆ X，则 X → Y
  • Java秒懂：如果你有一个完整的 User 对象(X)，你当然能获取到 User 里面的 Age 属性(Y)。大包小，理所当然。

2. 增广律 (Augmentation)

  • 顾名思义：增加、扩广。等式两边同时增加一样的筹码。
  • 公式：若 X → Y，则 XZ → YZ
  • Java秒懂：如果 订单ID(X) 能查出 商品名(Y)；那么 订单ID + 用户ID (XZ)，肯定能查出 商品名 + 用户ID (YZ)。两边同时加上Z，逻辑依然成立。

3. 传递律 (Transitivity)

  • 顾名思义：像接力棒一样传递。
  • 公式：若 X → Y，Y → Z，则 X → Z
  • Java秒懂：Service层(X)调用了Manager层(Y)，Manager层(Y)调用了Dao层(Z)。那么相当于Service层(X)间接调用了Dao层(Z)。

4. 合并规则 (Union)

  • 顾名思义：把相同条件推导出的不同结果合并打包。
  • 公式：若 X → Y，X → Z，则 X → YZ
  • Java秒懂：身份证(X)能查出姓名(Y)，身份证(X)也能查出性别(Z)。那我干脆写个接口，用身份证(X)直接返回一个包含[姓名, 性别](YZ)的DTO对象。

5. 伪传递规则 (Pseudo-transitivity)

  • 顾名思义：伪装的传递。中间人带了个“挂件”。
  • 公式：若 X → Y，WY → Z，则 XW → Z
  • Java秒懂：X能替换Y。既然 W + Y 能得到 Z，那我把里面的 Y 替换成 X，变成 W + X，照样能得到 Z。

6. 分解规则 (Decomposition) 👉 【本题考点】

  • 顾名思义：把大的结果拆分、分解成小的。
  • 公式：若 X → Y，Z ⊆ Y，则 X → Z
  • Java秒懂：如果 订单号(X) 能查出 完整的订单详情大礼包(Y)，而 商品单价(Z) 只是大礼包里的一件物品(Z ⊆ Y)。那么我用 订单号(X) 肯定也能单独查出 商品单价(Z)。

🖼️ 字符图解：分解规则 (Decomposition)

```text

[输入参数] [返回的大对象]

X ────推导────> Y

│

├─ 包含属性 A

├─ 包含属性 B

└─ 包含属性 Z <-- (因为 Z ⊆ Y)

既然 X 能拿到整个 Y，那 X 当然能拿到 Y 里面的 Z！

结论： X ────推导────> Z (这就是"分解"！)

```

回到您的2013年真题：题目问的是“分解规则”。

大脑立刻触发关键词：分解 = 把大结果拆成小结果。

  • A. 若 X→Y，Y→Z，则 X→Z
  • 顾问诊断：X传给Y，Y传给Z。这叫传递律。排除。
  • B. 若 Y⊆X⊆U，则 X→Y
  • 顾问诊断：Y是X的一部分，X推导出Y。自己推自己的一部分，这叫自反律。排除。
  • C. 若 X→Y，Z⊆Y，则 X→Z
  • 顾问诊断：X推导出大对象Y，Z是Y的一部分，所以X能推导出Z。把Y分解出了Z。这就是分解规则！正确！
  • D. 若 X→Y，Y→Z，则 X→YZ
  • 顾问诊断：这个选项其实是把传递律和合并规则杂糅了（实际上如果X→Y且Y→Z，根据传递律X→Z，再根据合并规则X→YZ是成立的），但它体现的是把Y和Z合并在一起，不是分解。排除。

给定关系R（A,B,C,D）和S（A,C,E,F），以下（）与$\sigma_{R.B > S.E}(R \bowtie S)$等价

子题1

参考答案：B

官方解析

本题考察的是关系代数中自然连接与选择、投影的等价变换。

自然连接 R ⋈ S 等价于在笛卡尔积 R × S 上施加同名属性相等的选择，再去掉重复同名属性进行投影，即 $σ_{1=5 ∧ 3=6}(R × S) $之后再做 π 去除重复列。

题干还包含选择条件，对应序号条件为$ σ{2 > 7}$。将三者合并即得到等价表达式$ π{1,2,3,4,7,8}(σ_{1=5 ∧ 2>7 ∧ 3=6}(R × S))$。

A选项：仅有 σ_{2>7}(R × S)，缺少自然连接所需的等值条件（1=5、3=6）以及最终的投影，不等价。

B选项：包含自然连接所需的两个等值条件（1=5、3=6），包含题干的选择条件（2>7），并在最后通过 π_{1,2,3,4,7,8} 去掉重复同名列，完全等价。

C选项：条件写作 2>'7' 将 7 当作字符常量，类型不匹配，且同样缺少自然连接的等值条件与投影，不等价。

D选项：虽含有等值连接条件与投影，但将 7 写成字符常量 '7'（应为数值 7），与题干语义不符，故不等价。

因此，选项 B 正确。

💡 一、 核心符号“顾名思义”记忆法（拒绝死记硬背）

对于英语不好、不想记学术名词的同学，我们直接看字面意思和符号长相：

1. $\times$ 笛卡尔积 —— 顾名思义：【无脑乘积】

  • 怎么记：乘号 $\times$ 就是把两张表的所有数据无脑交叉组合。
  • Java秒懂：两个嵌套的 for 循环，没有任何 if 判断。
  • SQL秒懂：SELECT * FROM R, S

2. $\sigma$ (Sigma) 选择 —— 顾名思义：【按条件选行】

  • 怎么记：$\sigma$ 长得像一个哨子。吹哨子叫停，符合条件的行（数据记录）才能通过。
  • Java秒懂：Java 8 Stream 的 .filter(条件)
  • SQL秒懂：WHERE 语句（比如 WHERE age > 18）

3. $\pi$ (Pi) 投影 —— 顾名思义：【光照投影留列】

  • 怎么记：$\pi$ 长得像一张桌子的腿，是一根一根竖着的。它代表竖着的“列”（字段）。投影就像从天上打一束光，只留下你想要的几根柱子（列）。
  • Java秒懂：Java 8 Stream 的 .map(提取某几个字段)
  • SQL秒懂：SELECT 字段1, 字段2（注意不是SELECT *）

4. $\bowtie$ 自然连接 —— 顾名思义：【自然而然地连起来】

  • 怎么记：$\bowtie$ 长得像一个蝴蝶结，把两张表绑在一起。既然是“自然”，就是两张表里名字相同的字段，自然而然就相等了，而且合并后，重复名字的字段只保留一个。
  • Java秒懂：把两个实体类按相同的属性名合并，去掉重复的属性。
  • SQL秒懂：INNER JOIN ... USING(同名字段)

🛠 二、 题目图解与推导（跟着步骤走，像Debug一样简单）

题干翻译：求 $\sigma_{R.B > S.E}(R \bowtie S)$ 的等价底层表达式。

大白话：先把 R 和 S 按同名字段自然连接（$\bowtie$），然后再过滤（$\sigma$）出 R表的B字段 > S表的E字段 的数据。

第一步：给字段排座位（打上数字编号）

考试时，底层表达式喜欢用数字代替字段名。我们画个图排个号：

```text

表 R (4个字段) 表 S (4个字段)

+---+---+---+---+ +---+---+---+---+

ABCDACEF
         

+---+---+---+---+ +---+---+---+---+

↓ ↓ ↓ ↓ ↓ ↓ ↓ ↓

1 2 3 4 5 6 7 8

```

第二步：拆解“自然连接” $\bowtie$ (蝴蝶结)

自然连接干了两件事：

  1. 找同名，加条件：R和S都有 A 和 C。所以条件是 R.A = S.A 且 R.C = S.C。
  • 换成数字就是：1 = 5 且 3 = 6
  1. 去重复，留列名：合并后，S表的 A (5) 和 C (6) 是多余的，扔掉。
  • 剩下的列（投影 $\pi$）是：1, 2, 3, 4, 7, 8

第三步：加上题干的额外过滤条件 $\sigma$ (哨子)

题干要求：R.B > S.E

  • 查上面的座位表：B是2，E是7。
  • 换成数字就是：2 > 7

第四步：组装代码 (像写SQL一样)

  1. FROM：先无脑组合两张表 $\rightarrow$ (R × S)
  2. WHERE：加上所有过滤条件（自然连接的条件 + 题干的条件） $\rightarrow$ σ_{1=5 ∧ 3=6 ∧ 2>7}
  3. SELECT：只保留去重后的列 $\rightarrow$ π_{1,2,3,4,7,8}

最终组装结果：$\pi{1,2,3,4,7,8}(\sigma{1 = 5 \land 2 > 7 \land 3 = 6}(R \times S))$ 👉 完美对应选项 B！

🚫 三、 避坑指南（为什么其他选项错？）

  • A选项：只有 2>7，忘了自然连接还要匹配同名字段（1=5, 3=6），也忘了去重列。（漏逻辑）
  • C选项：写成了 2>'7'。注意！这里的 7 代表的是第7列（S表的E字段），如果加了单引号 '7'，就变成字符串常量了！意思是“第2列的值大于字符串'7'”，完全改变了题意。（类型错误，Java程序员最懂这个痛）
  • D选项：和C一样，犯了加单引号 '7' 的致命错误。

A选项 内模式：内模式描述的是数据库中数据的物理存储结构和存储方式。它定义了数据的物理存储方式、存储记录的类型、物理顺序和索引等。内模式是数据库系统中与数据存储和优化相关的部分，并不涉及用户对数据的逻辑视图，因此不符合题意。

B选项 概念模式：概念模式描述了数据库中全体数据的逻辑结构和特征，是所有用户的公共数据视图。它是数据库的整体结构，涉及到数据库的完整性、约束等，但并不专门描述特定用户或应用程序的数据视图。因此，概念模式不是题干中所描述的部分。

D选项 物理模式：物理模式与内模式类似，主要关注数据在磁盘等存储介质上的物理布局和存储方式，不涉及用户视图或数据的逻辑结构。因此，这个选项不符合题意。

本题考察的是数据库事务的ACID特性。

A选项持久性（Durability）：表示一旦事务提交，其所做的修改会永久保存在数据库中，即使系统发生故障也不会丢失，属于事务的基本特性。

B选项原子性（Atomicity）：指事务是一个不可分割的操作单元，要么全部执行成功，要么全部失败回滚，属于事务的基本特性。

C选项一致性（Consistency）：表示事务执行前后，数据库必须从一个一致性状态转换到另一个一致性状态，属于事务的基本特性。

🧠 二、 顾名思义 · 核心记忆法（重点背诵区）

官方说事务有四个特性（简称ACID，英语不好没关系，我们直接记中文）。请看着汉字字面意思来记：

1. 原子性 (Atomicity) —— 对应选项B

  • 顾名思义：在初中物理里，“原子”是物质不可再分的最小单位。
  • 大白话：这个任务是个“原子”，不能被劈开。要么全做完，要么全不做。绝对不存在“只做了一半”的情况。

2. 一致性 (Consistency) —— 对应选项C

  • 顾名思义：“一致”就是一样、吻合、规矩没变。
  • 大白话：做任务之前和做任务之后，世界的“总规矩”保持一致。
  • 举例：张三给李四转账100块。转账前两人总共有500块，转账后两人总共还得是500块。总金额“一致”，不能凭空消失或多出来。

3. 隔离性 (Isolation) —— 题目未提，但考试必考

  • 顾名思义：“隔离”就是把你和我关在不同的房间，互相看不见。
  • 大白话：大家都在用数据库，你的 @Transactional 和我的 @Transactional 同时运行时，互相不能捣乱，就像被“隔离”了一样。

4. 持久性 (Durability) —— 对应选项A

  • 顾名思义：“持久”就是时间长、永久保留。
  • 大白话：只要代码里执行了 commit（提交成功），数据就持久地写死在硬盘上了。就算下一秒机房停电、服务器爆炸，数据也不会丢。

🚫 三、 为什么选 D (并发性) ？（防坑指南）

  • “并发”是用来形容“整个系统有多热闹”的（就像形容大街上人很多）。
  • 所以，并发性是数据库系统的能力，而不是单个事务的特性！

若关系R有m个元组，关系S有n个元组，则R和S的笛卡尔积有（）个元组。

官方解析

本题考察的是关系代数中笛卡尔积的基本概念。

笛卡尔积是关系代数中的一种二元操作，用于将两个关系中的每一个元组进行组合，生成一个新的关系。设关系R有m个元组，关系S有n个元组，则R×S表示所有可能的有序对 (r, s)，其中r∈R，s∈S。

A选项 n：只表示了S中的元组数，与笛卡尔积的结果无关，错误。

B选项 m：只表示了R中的元组数，也不正确。

因此，选项 D 正确。


1️⃣ 第一范式 (1NF) —— 顾名思义：【一就是一，不可再分】

  • 大白话：每个字段必须是原子的。比如“联系方式”不能填“手机:138, 邮箱:a@b.com”，必须拆成两个独立字段。

2️⃣ 第二范式 (2NF) —— 顾名思义：【二代表“两个”，不能只靠其中“一部分”】
  • 消除什么：消除非主属性对码的部分依赖。（本题考点！）
  • 大白话：如果主键是由两个字段组合而成的（比如 学号+课程号），那么普通字段（比如 学生姓名）不能只归其中一个管（姓名只跟学号有关，跟课程号无关，这就叫部分依赖）。必须拆表！

3️⃣ 第三范式 (3NF) —— 顾名思义：【拒绝“第三者”插足】
  • 消除什么：消除非主属性对码的传递依赖。

给定关系模式R \< U ，F \>， U= {A，B，C，D} ， F = {A→C ，AB→D }，则 R 的候选关键字为（）

子题1

参考答案：C

官方解析

本题考察的是关系数据库中候选键的判定，属于高频考点，需要熟练掌握。

候选键是指能唯一标识关系中元组的属性组合，且是最小的（即不包含冗余属性）。

根据题意： 属性集 U = {A, B, C, D}，函数依赖集 F = {A → C, AB → D}

我们通过属性闭包来判断候选键。

1. 计算 A⁺：

A⁺ = {A}，根据 A → C，A⁺ = {A, C}，无法推出 B 或 D，所以 A 不是候选键。

2. 计算 B⁺：

B⁺ = {B}，无法推出其他属性，B 不是候选键。

3. 计算 AB⁺：

AB⁺ = {A, B}，A → C ⇒ AB⁺ = {A, B, C}，AB → D ⇒ AB⁺ = {A, B, C, D}

AB 的闭包是全属性集 U，说明 AB 是超键，且 A⁺ 和 B⁺ 都不能独立推出全属性，说明 AB 是最小超键，即候选键。

4. 计算 C⁺：

C⁺ = {C}，不能推出其他属性，C 不是候选键。

因此，选项 C 正确。

(绝对不用专业名词解释专业名词，全是大白话)

1. 关系模式 R(a, b, c, d)

  • 顾名思义：“关系”在数据库里就是“一张二维表”。“模式”就是“表结构”。
  • 大白话：这就是一张有4个字段（a, b, c, d）的数据库表。你可以把它当成你SpringBoot项目里的一个 @Entity 实体类，里面有4个属性。

2. 函数依赖 (a → cd, c → b)

  • 顾名思义：“依赖”就是“靠你决定”。箭头 → 就是“顺藤摸瓜”。
  • 大白话：只要我知道了左边的值，就一定能查出右边的值。
  • a → cd：只要给我字段 a 的值，我就能确定 c 和 d 的值。
  • c → b：只要给我字段 c 的值，我就能确定 b 的值。
  • Java秒懂：相当于你写了一个方法 getCAndD(String a) 和 getB(String c)。

3. 候选键 (Candidate Key)

  • 顾名思义：“候选”就是“有资格竞选”，“键”就是“主键（唯一标识）”。合起来就是“主键的候选人”。

4. 属性闭包 (Attribute Closure)

  • 顾名思义：“闭”就是“封闭/包揽”，“包”就是“打包/滚雪球”。
  • 大白话：从某一个字段出发，通过“顺藤摸瓜（函数依赖）”，最多能滚出多大的雪球（找出多少个字段）。如果这个雪球能把表里所有字段都包进去，那这个出发点就是“候选键”。
