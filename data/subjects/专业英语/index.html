专业英语知识点结构化要点清单

2013年11月系统架构设计师真题

一、知识点名称

系统架构专业英语阅读理解（Professional English for System Architecture）

二、核心定义/结论

这类题本质是英文填空/选词，考的不是英语语法，而是：

  1. 认识专业术语的中文含义
  2. 根据上下文语境判断正确选项

涉及的核心概念域共五类：

① 软件架构三大结构

  • Module structures（模块结构）→ 静态代码单元
  • Component-and-connector structures（构件连接器结构）→ 运行时交互
  • Allocation structures（分配结构）→ 与非软件环境的映射

② 软件架构重构五步流程

  • Information extraction → Database construction → View fusion → Visualization & interaction → Pattern definition & recognition

③ 软件系统四大基本功能

  • Data storage → Data access logic → Application logic → Presentation logic

④ 非功能需求四类

  • Operational / Performance / Security / Cultural & Political requirements

⑤ C/S架构角色分工

  • Thin client（瘦客户端）/ Fat client（胖客户端）/ Database server / Web server / Application server

三、典型题型与解题要领

题型特征： 段落填空，每段5个空，选项均为英文词组

解题三步走：

```
↓

↓

第三步：排除明显错误项，锁定答案

```

四、易错点与注意事项

① 形近词混淆

  • Safety（人身安全）≠ Security（信息安全/防攻击）
  • Thin client（弱/只展示）≠ Fat client（强/能处理逻辑）
  • data storage（存数据）≠ data access logic（取数据的规则）
  • functional requirements（能做什么）≠ nonfunctional requirements（做得好不好）

② 范围大小陷阱

  • Reverse engineering（大概念）≠ Information extraction（具体步骤）
  • physical design（物理部署细节）≠ architecture design（整体技术蓝图）
  • data flow diagram（逻辑版）≠ physical data flow diagram（带网络节点的物理版）

③ 数据库类型易混

  • Legacy database = 遗留/过时技术的数据库（不是备份库）
  • Network database = 用指针连接记录（不是"联网的数据库"）
  • Hierarchical database = 树形一对多（不是网状多对多）

④ 三范式顺序

  • 1NF → 2NF → 3NF，第三范式是最优，不要选错方向

子题1

参考答案：C

官方解析

本题考察的是系统架构与软件架构三种主要结构分类。

问题1：

系统架构需要将系统的功能映射到软硬件组件上，这是系统架构的核心工作。

A选项 attributes：是质量属性，并非主要映射对象。错误。

B选项 constraint：约束条件，不是核心映射。错误。

C选项 functionality：功能，正确。

D选项 requirements：需求范围更大，不仅限于架构映射。错误。

因此选 C。

问题2：

系统架构的另一个映射是将软件架构映射到硬件架构。

A选项 physical components：指物理部件，不是体系结构。错误。

B选项 network architecture：仅描述网络结构，不是系统级核心。错误。

C选项 software architecture：正确。

D选项 interface architecture：侧重接口，不是全面的软件架构。错误。

因此选 C。

问题3：

模块结构（Module structures） 体现了作为一组代码或数据单元的决策，即静态结构。

A选项 Service structures：不属于三大类。错误。

B选项 Module structures：正确。

C选项 Deployment structures：属于分配结构，不是代码单元层次。错误。

D选项 Work assignment structures：属于分配结构，不是代码单元。错误。

因此选 B。

问题4：

构件-连接器结构（Component-and-connector structures） 体现了运行时的组件及交互方式，描述动态行为。

A选项 Decomposition structures：属于模块分解，不是运行时。错误。

B选项 Layer structures：静态分层结构。错误。

C选项 Implementation structures：代码实现相关，不是运行时交互。错误。

D选项 Component-and-connector structures：正确。

因此选 D。

问题5：

分配结构（Allocation structures） 体现了系统如何与非软件环境（硬件、网络、组织团队）关联。

A选项 Allocation structures：正确。

B选项 Class structures：属于面向对象建模，不是环境映射。错误。

C选项 Concurrency structures：涉及并发，不是环境映射。错误。

D选项 Uses structures：模块依赖，不是环境映射。错误。

因此选 A。

四、三大结构 · 一句话区分

```

静态代码块 → 模块结构 （你写代码时看到的）

动态运行时 → 构件连接器结构 （程序跑起来时看到的）

映射到环境 → 分配结构 （部署上线时看到的）

```

用你熟悉的 SpringBoot 类比：

```

模块结构 = 你的 controller / service / dao 包结构

构件连接器 = 服务启动后 Bean 之间的调用链路

分配结构 = 这个服务部署在哪台机器、哪个团队维护

```

第2题（题号：46）

专业英语 难度：0

Software architecture reconstruction is an interpretive, interactive, and iterative process including many activities. （）involves analyzing a system's existing design and implementation artifacts to construct a model of it. The result is used in the following activities to construct a view of the system. The database construction activity converts the （） contained in the view into a standard format for storage in a database. The （）activity involves defining and manipulating the information stored in database to reconcile, augment, and establish connections between the elements. Reconstruction consists of two primary activities: （） and （）. The former provides a mechanism for the user to manipulate architectural elements, and the latter provides facilities for architecture reconstruction.

子题1

参考答案：B

官方解析

本题考察的是软件架构重构（Software Architecture Reconstruction） 的主要过程与活动。

架构重构是一种通过分析已有系统的设计和实现工件，重建系统架构视图，并对架构进行理解、评估和改进的过程。它具有解释性、交互性和迭代性，通常包括信息提取、数据库构建、视图融合、可视化与交互、模式定义与识别等活动。

问题1：

A选项 Reverse engineering：广义上指对系统进行反向分析，但本题具体描述是分析现有设计与实现工件并构建模型，这更准确地称为信息提取，因此此项不够精准。

B选项 Information extraction：是指通过分析系统的设计与实现工件获取模型信息，用于后续的架构视图构建，符合题干描述，正确。

C选项 Requirements analysis：是需求阶段的活动，不是架构重构中分析现有系统的过程，错误。

D选项 Source code analysis：只是信息提取的一种手段，不等同于整个信息提取活动，错误。

问题2：

A选项 actors and use cases：属于需求建模阶段内容，不是架构视图中直接存储的元素。

B选项 processes and data：更贴近业务流程和数据建模，不是架构视图标准存储的核心结构。

C选项 elements and relations：架构视图的核心就是系统中的元素（components、modules等）及它们之间的关系，符合题干，正确。

D选项 schemas and tables：属于数据库结构，不是架构视图的直接描述内容。

问题3：

A选项 database normalization：是数据库设计的优化过程，与架构视图合并无关。

B选项 schema definition：定义数据库结构，不是融合架构视图的过程。

C选项 database optimization：是提升数据库性能的活动，非架构视图融合。

D选项 view fusion：是将不同视图的信息合并并建立联系的过程，正是题干描述的活动，正确。

问题4：

A选项 architecture analysis and design：是更高层次的架构活动，不是直接的可视化和交互过程。

B选项 domain analysis and static modeling：属于需求分析范畴，非架构重构的交互活动。

C选项 visualization and interaction：用于让用户以图形化、交互的方式操控架构元素，符合题干，正确。

D选项 user requirements modeling：是需求阶段的活动，不是架构重构核心步骤。

问题5：

A选项 pattern definition and recognition：在架构重构中用于识别、定义和匹配架构模式，帮助理解架构结构，符合题干，正确。

B选项 architecture design and implementation：是新的系统构建活动，不是重构中用于识别模式的过程。

C选项 system architecture modeling：虽然与架构相关，但不专指模式识别。

D选项 dynamic modeling and reconstruction：属于系统建模手段，不是模式定义和识别。

🔑 五个答案·顾名思义记忆法

> 原则：看中文名就知道是干什么的

答案① — 信息提取 (Information Extraction)

顾名思义： "提取信息" → 从老系统里把有用的信息挖出来

项目内容
干什么分析现有的代码、设计文档，建立系统模型
类比接手老项目第一件事：把所有代码翻一遍，搞清楚有哪些类、哪些模块
记忆口诀"提取" = 从已有东西里抽出有价值的内容

❌ 为什么不选"逆向工程"：逆向工程是大概念（像"开发"这个词），信息提取才是这一步具体在做的事（像"写代码"这个词）

答案② — 元素与关系 (Elements and Relations)

顾名思义： "元素" = 系统里的零件；"关系" = 零件之间怎么连的

项目内容
干什么架构视图存进数据库的核心内容
类比你画系统架构图，图上有方块（元素：模块、组件、服务）和箭头（关系：调用、依赖、继承）
记忆口诀架构图 = 方块 + 箭头 = 元素 + 关系

❌ 为什么不选"流程与数据"：那是业务流程图的内容，不是架构图的核心

答案③ — 视图融合 (View Fusion)

顾名思义： "融合视图" → 把多个角度看到的东西合并在一起

项目内容
干什么把数据库里的信息整合、补充缺失内容、建立元素间的连接
类比你从代码里提取了模块信息，从配置文件里提取了部署信息，现在把这两份信息合并成一张完整的图
记忆口诀"融合" = 多份信息合体，消除矛盾，补全缺失

❌ 为什么不选"数据库规范化"：那是数据库设计优化，跟架构视图合并没关系

答案④ — 可视化与交互 (Visualization and Interaction)

白话理解：

同一份数据，A系统存一份，B系统也存一份，到处都是重复的——这就是数据冗余。

题目说"相同数据存在多个地方"，就是它。

3️⃣ entity-relationship diagram　→　选 A（第三空）

顾名思义拆解：

```

entity = 实体（现实中真实存在的东西，比如"用户""订单"）

relationship = 关系（实体之间怎么连接的）

diagram = 图（画出来的图）

entity-relationship diagram = 实体关系图 = E-R图

```

白话理解：

你画过数据库设计图吗？那个画"用户——下单——订单"的图就是它。

题目说"展示系统实体逻辑关系的模型图"，就是E-R图。

> 💡 程序员联想：你用 Spring Boot 设计数据库表之前，画的那个"方框+连线"的设计图，就是 E-R 图。

4️⃣ Normalization　→　选 A（第四空）

顾名思义拆解：

```

Normal = 正常的、规范的

-ization = 变成...的过程（动作后缀）

Normalization = 让数据变规范的过程 = 规范化

```

白话理解：

设计数据库表时，把字段合理分配到各个表里，并确定主键——让表结构变得"规规矩矩"的过程。

题目说"给每张表分配字段、确定主键的过程"，就是规范化。

5️⃣ third normal form　→　选 D（第五空）

顾名思义拆解：

```

third = 第三

normal = 规范

form = 形式/范式

third normal form = 第三范式 = 3NF

```

三个范式的"升级打怪"记忆：

```

┌─────────────────────────────────────────┐

│ 第一范式(1NF) → 字段不能再拆分 │

│ ↓ 升级 │

│ 第二范式(2NF) → 消除"部分依赖" │

│ ↓ 升级 │

│ 第三范式(3NF) → 消除"传递依赖"★最优 │

└─────────────────────────────────────────┘

```

白话理解：

三个范式是从低到高的"数据库设计等级"，第三范式是业务数据库的最优设计标准。

题目说"三个范式中代表最佳设计的"，就是第三范式。

🧠 顾名思义记忆法·核心词汇

1️⃣ Client/Server System — 客户/服务器系统

```

【顾名思义】

"客户" + "服务器" = 客户来点菜，服务器来做菜

整个餐厅的运营模式 = Client/Server System

【本质】

把"界面展示、逻辑处理、数据存储"

分散到客户端和服务器两边来完成的分布式架构

```

2️⃣ Thin Client — 瘦客户端

```

【顾名思义】

"瘦" = 功能少、配置低、很轻量

就像餐厅里只负责"传菜"的服务员

——不做菜、不管库存，只把菜端给客人（展示界面）

【记忆口诀】

瘦子力气小 → 处理器弱、内存小

只管"脸面" → 只负责用户界面展示

```

3️⃣ Fat Client — 胖客户端

```

【顾名思义】

"胖" = 功能多、配置高、能力强

就像餐厅里的"大厨兼采购"

——自己能处理很多事情

【记忆口诀】

胖子力气大 → 处理器强、内存大、存储多

能干很多活 → 本地可以跑业务逻辑

【对比记忆】

瘦客户端 🤏 ←→ 胖客户端 💪

只展示界面 功能强大能处理逻辑

```

4️⃣ Database Server — 数据库服务器

```

【顾名思义】

"数据库" + "服务器"

= 专门管"仓库"的大管家

就像餐厅的"食材仓库管理员"

——所有食材（数据）都在他这里

——所有取食材的命令（数据库命令）都由他执行

【关键特征】

托管共享数据库 + 执行所有数据库命令

```

5️⃣ Web Server — 网页服务器

```

【顾名思义】

"Web" 就是"网页/网站"

= 专门管网站的服务器

就像餐厅的"外卖接单员"

——管理网站内容

——客户来访问，就把网页和数据返回给他

【关键特征】

托管网站 + 与客户端通信 + 返回文档和数据

```
