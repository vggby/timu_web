范围管理 · 结构化知识点清单

知识点名称

项目范围管理 —— 范围定义过程（输入、概念辨析）

核心定义/结论

产品范围 vs 项目范围

  • 产品范围：做出来的东西有什么功能
  • 项目范围：为了做出来，需要完成的所有工作

范围定义的作用

  • 是制定项目计划（时间/成本/资源）的基础
  • 核心任务是"划边界"：哪些做、哪些不做

范围定义的标准输入（口诀：章管资批）

口诀字输入项白话理解
章项目章程项目立项文件，说明目标和边界
管项目范围管理计划指导"怎么定范围"的规则手册
资组织过程资产公司历史经验、模板、教训
批批准的变更申请已盖章审批通过的变更单

典型题型与解题要领

题型1：判断哪项"不属于"范围定义的输入（题17）

解题要领：找那个"听起来像项目管理，但跟定范围没直接关系"的选项。文档管理方法、质量标准、可交付物说明 → 出现即排除。

题型2：概念辨析选正确描述（题18）

解题要领：用"顾名思义"排除法，重点识别产品范围/项目范围/范围定义三者的区别，以及逻辑顺序（产品范围说明书 → 项目范围说明书）。

题型3：从选项中选出完整正确的输入组合（题16）

解题要领：对照"章管资批"四项逐一核对，重点卡两个细节：

  • "变更申请"前必须有"批准的"
  • "产品范围说明书"是输出不是输入，出现即排除

易错点与注意事项

  • "变更申请"≠"批准的变更申请"，没有"批准的"三个字就是错的
  • 产品范围说明书是范围定义的输出/依据来源，不是输入，常作为干扰项出现
  • 项目范围 ≠ 产品功能，混淆这两个概念是最高频的错误
  • 产品范围说明书和项目范围说明书的顺序不能反：先有产品范围，再有项目范围
  • 文档管理方法、质量标准、系统需求说明 → 属于其他过程，不是范围定义输入

推荐复习顺序

  1. 先区分"产品范围"和"项目范围"的概念，这是所有题目的基础
  2. 记住"范围定义是项目计划的基础"这一核心结论
  3. 背"章管资批"四字口诀，对应四个标准输入
  4. 练习排除干扰项：重点识别"批准的"关键词 + "产品范围说明书不是输入"
  5. 最后做真题验证，能在10秒内排除错误选项即达标

进度管理 · 结构化知识点清单

知识点名称

项目时间管理（进度管理）

核心定义/结论

时间管理六大过程（口诀：定排资时计控）

```

活动定义 → 活动排序 → 资源估算 → 历时估算 → 制定计划 → 进度控制

```

关键路径法（CPM）

  • 关键路径 = 从开始到结束耗时最长的路径
  • 关键路径长度 = 项目总工期
  • 总时差 = 关键路径长度 - 该任务所在路径长度

三点估算法

```

期望天数 = （最小 + 4×最可能 + 最大）÷ 6

```

赶工优化（费用斜率法）

```

费用斜率 = （赶工直接费 - 正常直接费）÷（正常天数 - 赶工天数）

赶工合算条件：节省的间接费 > 增加的直接费

```

典型题型与解题要领

题型一：六大过程识别（选择题）

  • 要领：认出完整的六个名词，排除缺项或混入无关概念的选项

题型二：活动定义工具

  • 要领：活动定义用 WBS；Gantt 用于展示进度；PERT 用于依赖估算

题型三：总时差计算

  • 要领：
  1. 整理依赖关系表
  2. 画双代号网络图
  3. 列出所有路径及长度
  4. 总时差 = 最长路径 - 目标任务所在路径

题型四：赶工费用优化

  • 要领（五步口诀）：
  1. 画网络图，找关键路径
  2. 算各工序费用斜率
  3. 优先压斜率最小的工序
  4. 多条关键路径时必须同时压缩
  5. 每步判断：节省间接费 > 增加直接费 → 继续，否则停止

易错点与注意事项

  • 六大过程容易漏掉"资源估算"或"历时估算"，两个"估算"都要有
  • WBS 是活动定义的工具，不是进度展示工具，别和 Gantt 混淆
  • 三点估算中"最可能"权重是 4，不是简单平均
  • 出现双关键路径后，压缩单条路径无效，必须两条同时压
  • 公共工序（如 A 在分叉前）压缩一次等于同时缩短所有经过它的路径，性价比高
  • 赶工不能无限压缩，注意题目给出的最短天数限制

推荐复习顺序

  1. 先背六大过程口诀"定排资时计控"，能默写并解释每步含义
  2. 理解 WBS / Gantt / PERT 各自用途，区分清楚
  3. 练习画双代号网络图，从依赖关系表到图的转换要熟练
  4. 掌握关键路径识别和总时差计算（先做第39题、第44题）
  5. 最后攻关赶工优化计算（第43题、第61题），按五步口诀逐步推导

配置管理 · 结构化知识点清单

知识点名称

配置管理（软件配置管理 / SCM）

核心定义/结论

产品配置：产品生命周期各阶段产生的所有形式和版本的 文档、计算机程序、部件及数据 的集合（四类缺一不可）

配置项：产品配置集合中的每一个元素，即产品形成过程中的工作成果，经正式审批后成为软件配置项

配置项三种状态：草稿 → 正式发布 → 正在修改

变更控制委员会（CCB）：负责审批变更请求的组织，可根据项目需要设立多个，有权拒绝变更

典型题型与解题要领

题型1：配置项状态判断

  • 题目问"配置项状态包括哪些"
  • 解题要领：状态必须是"名词性的阶段描述"，排除含有动作/过程/事件的选项（如"技术评审"、"版本变更"是动作，不是状态）

题型2：什么属于/不属于配置项

  • 解题要领：问自己"这个东西是为了造产品产生的吗？"
  • 工作计划、进度计划、项目计划 → 永远不是配置项
  • 文档、代码、数据、可执行文件 → 永远是配置项

题型3：产品配置的完整定义

  • 解题要领：找"最全的那个选项"，必须同时包含文档、程序、部件、数据四类

题型4：变更控制描述正误判断

  • 解题要领：警惕"只能/必须/不能"等绝对化表述，通常就是错误选项

题型5：阶段产物经审批后称为什么

  • 记住：阶段产物 + 经过审批 = 软件配置项（不是产品、不是版本、不是里程碑）

易错点与注意事项

易错1：把"过程/动作"当成"状态"

  • "技术评审"、"评审或审批"、"版本变更" 都是动作，不是配置项的状态
  • 配置项状态只有三个：草稿、正式发布、正在修改

易错2：把"工作计划"当成配置项

  • 工作计划是项目管理成果，不是产品组成部分，不纳入配置管理

易错3：认为CCB只能有一个

  • CCB可以按项目需要设立多个，可按变更类型分组

易错4：混淆配置项、版本、产品三个概念

概念含义
配置项单个阶段产物，经审批后的叫法
版本多个配置项的集合，某一发布状态
产品最终交付给客户的完整系统

易错5：产品配置定义记不全

  • 只记文档和代码，漏掉"部件"和"数据"，导致选了不完整的选项

推荐复习顺序

  1. 先理解"配置项"的定义——产品生命周期中的工作成果，经审批后称为配置项
  2. 记住产品配置的四类组成：文档、计算机程序、部件、数据
  3. 记住配置项三种状态及其顺序：草稿 → 正式发布 → 正在修改
  4. 掌握"什么不是配置项"的判断方法：工作计划类 = 项目管理成果 = 不是配置项
  5. 最后了解变更控制的基本原则：CCB可多个、可用工具、可拒绝变更、与其他配置活动密切相关

> 整体难度不高，属于概念辨析类考点，理解中文含义即可做对，无需深入记忆流程细节。

成本管理知识点结构化要点清单

知识点名称

项目成本管理流程（四大子过程）

核心定义/结论

成本管理包含四个顺序推进的子过程：

子过程核心动作输出结果
成本估算近似计算完成项目所需总费用总成本估算值
成本预算将总成本分配到各活动/工作包成本基线
成本跟踪监控实际支出与预算的偏差偏差报告
成本控制根据偏差采取纠正措施变更请求/调整方案

关键结论：成本基线由成本预算过程产生，是后续控制的参照标准。

典型题型与解题要领

典型题型：概念辨析选择题（如本题）

解题要领只有一条：抓住每个子过程的"动作关键词"

  • 看到"估算/近似计算总费用" → 成本估算
  • 看到"分配到工作包/建立基线" → 成本预算
  • 看到"监控/跟踪偏差" → 成本跟踪
  • 看到"纠正/控制超支" → 成本控制

记忆口诀：估总数 → 分到包 → 盯偏差 → 出手管

易错点与注意事项

  1. 成本估算 vs 成本预算 最容易混淆
  • 估算只产生一个总数字，不做分配
  • 预算才是把钱"切块"分配，形成基线
  • 区分点：有没有"分配"和"基线"这两个词
  1. 成本跟踪 vs 成本控制 容易搞反
  • 跟踪 = 发现问题（被动监控）
  • 控制 = 解决问题（主动干预）
  1. "成本基线"归属不要记错，它是成本预算的输出，不是成本估算的输出

推荐复习顺序

  1. 先理解四个子过程的顺序关系（估→预→跟→控），建立整体框架
  2. 重点攻克"成本预算"的定义，因为它是高频考点（分配+基线）
  3. 对比记忆"估算 vs 预算"、"跟踪 vs 控制"两组易混概念
  4. 做2~3道历年选择题验证理解，重点看题干里的动作关键词
  5. 最后回顾成本基线的归属，确认不会混淆

管理工具 · 知识点结构化要点清单

知识点名称

软件文档分类（用户文档 vs 系统文档）

核心定义/结论

软件文档分为两大类：

用户文档：面向使用者，帮助其安装、操作、使用软件。

包括：安装手册、使用说明书、参考手册、操作手册、版本说明

系统文档：面向开发者/维护者，记录软件开发全过程。

包括：需求分析、系统设计、概要设计、详细设计、编码规范、测试计划

典型题型与解题要领

题型：给出若干文档名称，判断哪个"不属于用户文档"或"属于系统文档"。

解题要领只需一个判断句：

> "普通用户拿到这份文档，有实际用处吗？"

> 有用 → 用户文档；看不懂/不需要 → 系统文档

高频考点对照：

文档名称类型
安装手册用户文档
参考手册用户文档
版本说明用户文档
使用说明书用户文档
系统设计系统文档
需求分析系统文档
测试计划系统文档

易错点与注意事项

  • "版本说明"容易被误判为系统文档，实际上它是告知用户更新内容的，属于用户文档
  • "参考手册"容易被误判为系统文档，实际上它是供用户查阅命令/参数的工具书，属于用户文档
  • "系统设计"名字里有"系统"二字，但这里的"系统"指的是软件系统的内部架构，不是"系统文档"的"系统"，注意别被字面迷惑——判断依据始终是"受众是谁"

推荐复习顺序

  1. 先记住两类文档的受众区别（使用者 vs 开发维护者）
  2. 背熟用户文档的典型清单（安装、使用、参考、操作、版本）
  3. 用"用户有没有用"的判断句做几道真题验证
  4. 重点记住易错项：版本说明、参考手册属于用户文档；系统设计属于系统文档

官方解析

本题考察的是项目范围管理中“定义范围”过程的输入内容。

A选项项目章程：是范围定义的重要输入之一，它提供了高层次的项目描述、目标、主要干系人和总体边界，为后续的范围界定提供了基本依据，因此属于有效输入。

B选项项目范围管理计划：是项目管理计划中的组成部分，定义了如何制定、监控和控制项目范围，是指导范围定义工作的主要依据，也属于该过程的输入。

C选项批准的变更申请：虽然不是PMBOK第六版以后定义范围过程的标准输入，但在一些老版本教材或项目调整背景中，作为变更引发重新定义范围的触发条件，也有可能被提及，因此并不完全错误。

D选项项目文档管理方法：是项目整体管理中的一部分，涉及文档的创建、控制与存储方式，与具体的范围定义过程无直接关系，不属于定义范围的输入。

因此，正确答案是 D。

第2题（题号：18）

进度管理 难度：0

活动定义是项目时间管理中的过程之一，（）是进行活动定义时通常使用的一种工具。

子题1

参考答案：C

官方解析

本题考察的是项目管理中的活动定义过程及其常用工具。

在项目管理中，活动定义是将工作分解结构（WBS）中定义的工作包细化为具体的活动。通过细化工作包，项目管理者能够明确每个具体活动的执行内容、时间和责任。为帮助进行活动定义，常用的工具之一就是工作分解结构（WBS）。

📒 软考笔记 · 成本管理四兄弟

🧠 顾名思义记忆法

把"成本管理"想象成盖房子收钱的四个步骤：

```

先算钱 → 再分钱 → 盯着花 → 管超支

↓ ↓ ↓ ↓

成本估算 成本预算 成本跟踪 成本控制

```

四个概念逐个拆解

💰 成本估算

> "估"= 估摸着算，还没定

就是项目开始前，大概算一下整个项目要花多少钱。

比如你接了个外包项目，先粗算一下："这活大概要花20万"。

→ 结果是一个总数字，还没细分到每个任务。

📊 成本预算 ⭐（本题答案）

> "预"= 预先分好，"算"= 算清楚每块

就是把上面估算出来的总钱数，切分到每个具体任务上。

比如：总共20万 → 设计5万、开发10万、测试5万。

→ 切分完之后形成的那张"钱的分配表"就叫 成本基线（可以理解为"花钱的标准线"）。

```

总成本20万

├── 设计模块 5万

├── 开发模块 10万

└── 测试模块 5万

↑

这张表 = 成本基线

```

👀 成本跟踪

> "跟踪"= 跟着盯，看钱花到哪了

项目进行中，盯着实际花了多少钱，和预算对比有没有偏。

比如：开发模块预算10万，现在已经花了12万，超了！

→ 只是发现问题，不负责解决。

🔧 成本控制

> "控制"= 发现超了就出手管

发现花超了之后，采取行动去纠正，比如砍需求、调资源。

→ 是解决问题的那一步。

🔁 四步顺序口诀

```

估（估算总钱）→ 预（预先分钱）→ 跟（跟踪花钱）→ 控（控制超钱）

```

> 就像发工资：先算工资总额 → 再分配各部门 → 月中盯着花销 → 超了就踩刹车

✅ 考试只需掌握到这个程度

成本估算算总数，不分配
成本预算把总数分到各任务，形成基线 ← 重点
成本跟踪盯着花，发现偏差
成本控制发现偏差后去纠正

本题考察的是软件文档分类中用户文档与系统文档的区别。

用户文档是为终端用户或操作员准备的，用于指导其正确安装、使用和操作软件。典型的用户文档包括：安装手册、使用说明书、参考手册、操作手册、常见问题解答、版本说明等。

系统文档主要是为软件开发人员和维护人员编写的，记录了从需求分析、系统设计、编码、测试到部署的全过程内容。这类文档对程序的理解和维护非常关键。

A选项系统设计：属于系统文档的范畴，用于描述系统架构、模块划分、接口设计等，不是用户需要了解的内容，正确。

B选项版本说明：向用户说明软件的更新内容、修复的问题和新功能，是用户了解系统变更的依据，属于用户文档，错误。

C选项安装手册：指导用户如何正确安装软件系统，是典型的用户文档，错误。

D选项参考手册：提供系统命令、参数、接口使用等详细说明，辅助用户深入使用系统，属于用户文档，错误。

🧠 核心知识点拆解

一、三点估算法

> 顾名思义：三个点（最小、最可能、最大）估算出一个期望值

公式：

```

期望天数 = （最小 + 4×最可能 + 最大）÷ 6

```

本题套入：

```

C的期望天数 = （5 + 4×14 + 17）÷ 6

= （5 + 56 + 17）÷ 6

= 78 ÷ 6

= 13天

```

为什么最可能要乘以4？

因为"最可能"发生的概率最高，权重最大，所以占4份，另外两个极端各占1份，总共6份取平均。

```

```

```

C所在路径长度 = 5（A）+ 13（C）+ 3 + 4 = 25天

C的总时差 = 27 - 25 = 2天

🧠 顾名思义记忆核心概念

关键路径 = "关键的那条最长路"

> 项目里从头到尾耗时最长的那条工序链，它决定整个项目最早几天能完成。哪条路最长，哪条就是关键路径。

赶工 = "花钱买时间"

> 给工人发加班费，让他们提前完工。钱花得越多，完工越早，但人有极限，不能无限压缩。

直接费用 = "干活的钱"

> 直接花在这道工序上的钱，比如工人工资、材料费。赶工会让这个变多。

间接费用 = "每天都要烧的钱"

> 不管干不干活，每天都要花的钱，比如办公室租金、管理费。工期越长，这个越多。

费用斜率 = "每提前一天要多花多少加班费"

> 公式：(赶工直接费 - 正常直接费) ÷ (正常天数 - 赶工天数)

> 斜率越小 = 加班费越便宜 = 优先压缩这道工序

```

增加直接费：2×2 = 4万

节省间接费：2×4.5 = 9万

净节省：9-4 = 5万 ✅ 划算

工期：12→10天 总费用：99-5 = 94万

此时路径耗时：

A-B : 3+4 = 7天

A-C-D : 3+4+3 = 10天 ← 两条都是关键路径了！

```

第二步：同时压缩B和D（两条关键路径各压1天）

```

间接费=4.5万/天

增加直接费：(1+2)×1 = 3万

节省间接费：1×4.5 = 4.5万

净节省：4.5-3 = 1.5万 ✅ 划算

工期：10→9天 总费用：94-1.5 = 92.5万

此时路径耗时：

A-B : 3+3 = 6天

A-C-D : 3+4+2 = 9天 ← 仍是两条关键路径

```

第三步：压缩公共工序A（两条路径都经过A）

```

增加直接费：2×4 = 8万

节省间接费：2×4.5 = 9万

净节省：9-8 = 1万 ✅ 划算

工期：9→7天 总费用：92.5-1 = 91.5万

此时路径耗时：

A-B : 1+3 = 4天

A-C-D : 1+4+2 = 7天 ← 关键路径

间接费 = 4.5万/天

第17题（题号：11）

配置管理 难度：0

软件生存周期各个阶段活动的产物经审批后即可称之为（）。

子题1

参考答案：B

官方解析

本题考察的是需求变更管理和软件配置管理的相关知识。

A选项产品：产品是最终交付给客户的系统或软件，通常是在多个阶段的开发过程中逐步形成的，但并不专指经过审批的阶段产物。它更强调最终交付成果，而不是开发过程中每个阶段的产物。

B选项软件配置项：软件配置项是指在软件生存周期各个阶段（如需求、设计、开发等）产出的成果，经过正式审批和确认后，成为软件配置项。软件配置项是配置管理的基础，经过变更控制和版本管理，确保产品开发的一致性和稳定性。

C选项版本：版本是指软件的特定发布或发布状态，通常包括多个软件配置项。在开发过程中，版本是由不同的配置项组成的，并非直接代表各阶段的产物。版本发布需要经过配置管理，但并不等同于阶段产物的审批结果。

D选项里程碑：里程碑是项目进度中的关键节点，用于标识项目的重要阶段和成就。它并不指代具体的产物，而是项目管理中的时间标记。

因此，选项 B 正确。
