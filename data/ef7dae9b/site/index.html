📑 知识点归纳清单：需求工程 (重点：需求管理与基线)

一、 知识点名称

需求工程（Requirements Engineering）

(注：本次真题主要聚焦于需求工程中的“需求管理”子领域及“需求基线”概念)

二、 核心定义/结论

需求工程在宏观上分为两大阵营：需求开发（从无到有） + 需求管理（维护控制）。

1. 需求工程的宏观划分（核心考点）

  • 需求开发（生孩子）：包含需求获取、需求分析（建模）、需求定义（描述）、需求评审。标志着需求从模糊到清晰的过程。
  • 需求管理（养孩子）：需求评审通过后，对需求进行维护和控制的过程。

2. 需求管理的核心活动（记忆口诀：变、版、跟、态）

  • 变更控制（变）：控制需求的修改，必须走审批流程（类似代码合并前的 Code Review 和审批）。
  • 版本控制（版）：标识需求文档的不同版本，防止混乱（类似 Git Tag 或分支管理）。
  • 需求跟踪（跟）：建立需求与后续架构、设计、源代码、测试用例之间的联系文档（类似微服务中的 TraceId 全链路追踪）。
  • 需求状态跟踪（态）：跟踪需求当前处于什么阶段（类似 Jira/禅道 上的任务看板状态）。

3. 关键产出物定义

  • 需求基线（Baseline）：需求文档经过评审批准后形成的正式约定，是后续开发工作的基础/底线（相当于在Git中打了一个 v1.0.0 的Tag，之后不能随便改，改了要走变更流程）。
  • 需求约定（Agreement）：需求基线在客户和开发者之间构筑的桥梁和契约（相当于前后端定好的 Swagger API 接口文档，双方按此履约）。
三、 典型题型与解题要领

题型 1：区分“需求开发”与“需求管理”活动（找茬题）

  • 题干特征：问“以下哪个属于/不属于需求管理的主要活动？”
  • 解题要领：
  • 看到“获取、分析、建模、定义、评审” ➡️ 属于【需求开发】（前期工作）。
  • 看到“变更、版本、跟踪、状态” ➡️ 属于【需求管理】（后期工作）。
  • 秒杀技巧：选项中出现“文档管理”，直接选它作为“不属于”的答案（文档管理属于配置管理/项目管理范畴，是管文件的，不是管需求逻辑的）。

题型 2：概念填空与匹配题（基线与约定）

  • 题干特征：描述一段话，问这是什么概念（如“经过评审批准后”、“构筑了桥梁”）。
  • 解题要领：
  • 抓取关键词：看到“评审批准”、“开发工作的基础” ➡️ 选【需求基线】。
  • 抓取关键词：看到“客户和开发者之间”、“桥梁” ➡️ 选【需求约定】。
  • 避坑：不要选带有“标准”的选项（如需求标准），标准是公司规范，不是具体项目的产出物。

题型 3：需求跟踪的定义识别题

  • 题干特征：问编制需求与系统元素（代码、测试等）联系的文档是什么。
  • 解题要领：
  • 抓取关键词：看到“联系文档”、“映射”、“源代码/测试” ➡️ 选【需求跟踪】。
  • 联想记忆：顺藤摸瓜找Bug，把需求、代码、测试串起来的线索就是“跟踪”。
四、 易错点与注意事项
  1. 易错点：将“文档管理”等同于“需求管理”
  • 纠正：文档管理只是给文件命名、存档（打杂活）；需求管理是管理需求内容的演进和变更（核心业务逻辑）。两者不在一个层级。
  1. 易错点：混淆“需求分析”与“需求跟踪”
  • 纠正：需求分析是开会讨论“能不能做、优先级是什么”；需求跟踪是画表格（需求跟踪矩阵）记录“这个需求对应哪行代码、哪个测试用例”。
  1. 注意事项：基线的前后界限
  • 需求评审前 ➡️ 属于需求开发阶段，需求可以随时改。
  • 需求评审后 ➡️ 形成需求基线，进入需求管理阶段，修改必须走“变更控制”流程。
五、 推荐复习顺序（符合认知逻辑）

建议您按照以下“软件生命周期”的时间轴顺序进行脑内推演复习：

  1. 第一步：理清宏观边界
  • 先复习【需求工程】的整体架构，明确“需求开发”和“需求管理”的分界线。
  1. 第二步：掌握分界点（里程碑）
  • 复习【需求基线】与【需求约定】的概念。理解它们是如何作为“开发”的结束和“管理”的开始的（Git打Tag的瞬间）。
  1. 第三步：深挖管理核心（变、版、跟）
  • 重点记忆需求管理的四大活动（变更控制、版本控制、需求跟踪、状态跟踪）。
  1. 第四步：单点突破（需求跟踪）
  • 单独复习【需求跟踪】的定义，理解它如何将需求与下游的架构、代码、测试串联起来（TraceId全链路追踪）。

(备考提示：该知识点在架构师考试中属于“概念辨析题”，无需默写，只要能在考场上通过关键词和日常开发场景（Git/Jira）产生条件反射，即可轻松拿满分！)

第1题（题号：18）

需求工程 难度：1

需求管理是一个对系统需求变更、了解和控制的过程。以下活动中，（）不属于需求管理的主要活动。

子题1

参考答案：A

官方解析

本题考察的是需求管理的三大核心活动。

需求管理的核心任务是在整个软件开发生命周期中跟踪、控制和管理需求的变更和状态，确保系统按需构建并满足用户需求。需求管理主要包括以下三个方面：

1. 变更控制：确保对需求变更进行严格的审批、记录与跟踪，防止无序变更，是需求管理的基础机制之一。

2. 版本控制：用于识别不同版本的需求文档，记录需求在时间上的演变，支持对不同版本间的比较和回退。

3. 需求跟踪：确保每一个需求都能从提出到实现、测试都有迹可循，即“需求的前向与后向可追溯性”。

A选项文档管理：尽管文档管理对整个项目来说很重要，但它并不是需求管理的核心组成部分，而是配置管理、项目管理中更广泛的一个内容，正确。

B选项需求跟踪：是需求管理的重要活动之一，错误。

C选项版本控制：用于管理需求文档及其变更，属于需求管理内容，错误。

D选项变更控制：管理需求变更流程的重要机制，属于需求管理内容，错误。

因此，选项 A. 文档管理 正确。

🌟 架构师备考专属笔记：需求管理三大核心 🌟

1️⃣ 核心概念大白话翻译（拒绝专业词汇套娃）

在软件开发里，“需求管理”其实就是“对付产品经理频繁改需求的一套打法”。

产品经理今天加个按钮，明天删个接口，如果我们不“管理”，项目就乱套了。为了不乱套，我们只需要做三件事：

  • 变更控制：不能你想改就改，得走审批。（相当于代码合并前的 Code Review 和审批）
  • 版本控制：改了之后，得知道哪版是哪版。（相当于咱们用的 Git 或 SVN）
  • 需求跟踪：这个需求到底写没写成代码？测没测试？得能查到。（相当于咱们在SpringBoot里打的 Log 日志，得能顺藤摸瓜）

2️⃣ 顾名思义记忆法（核心背诵区）

我们把这三个词拆开，看字面意思就能记住：

💡 记忆口诀：【变、版、跟】

👉 联想场景：产品经理（老板）又变卦了，赶紧打个新版本，跟上去！

  • 【变】变更控制
  • 顾名思义：变（变化）更（更改）控（控制）。
  • 怎么记：需求发生了“变化和更改”，我们要把它“控制”住，不能悄悄改。
  • 【版】版本控制
  • 顾名思义：版（版次）本（文本）控（控制）。
  • 怎么记：需求文档V1.0变成V2.0，对这些“不同版次的文本”进行“控制”。
  • 【跟】需求跟踪
  • 顾名思义：跟（跟进）踪（踪迹）。
  • 怎么记：需求就像一个犯人，我们要“跟进”它的“踪迹”，看它最终变成了哪行代码，哪个测试用例。

3️⃣ 字符图解记忆（右脑图像记忆）

您可以把需求管理想象成一个“漏斗与流水线”：

```text

[产品经理提出各种想法]

│

▼

+-----------+

| 需求管理 | <-- 核心目的：不让项目失控

+-----------+

│

├─▶ 1. 变 (变更控制) 🛑 设关卡：同意改吗？(防乱改)

│

├─▶ 2. 版 (版本控制) 📚 贴标签：这是第几版？(防弄混)

│

└─▶ 3. 跟 (需求跟踪) 👣 留脚印：代码写到哪了？(防遗漏)

```

4️⃣ 避坑指南：为什么选 A (文档管理)？

  • 文档管理：顾名思义，就是“管文件”（比如把Word文档存在哪个文件夹，怎么命名）。
  • 为什么它不是核心？ 因为管文件是个打杂的活儿（属于“配置管理”或“项目管理”的范畴）。需求管理的核心是管“需求本身的内容和变化”，而不是管那个装需求的Word文件。
  • 程序员秒懂：文档管理就像是给电脑分C盘D盘建文件夹；而需求管理是你用Git去管理代码的逻辑演进。两者完全不在一个维度。

🧠 核心概念“顾名思义”与“Java秒懂”

##### 1. 需求基线 (Requirement Baseline) —— 对应第一空

  • 顾名思义拆解：
  • 基 = 基础（盖楼打的地基）
  • 线 = 底线 / 红线
  • 连起来记： 打好基础后画的一条红线。过了这条线，就不能随便乱动了。
  • ☕ Java程序员秒懂：
  • 这就相当于您在Git里打了一个 Tag (v1.0.0)，或者把代码合并到了 Master/Main 分支。
  • 在打Tag之前（需求开发阶段），代码随便改；一旦打了Tag（评审批准后），这就是基线。后续如果产品经理还想加功能？对不起，不能直接改了，得走正规的“需求变更”流程（提新的Issue和PR）。

##### 2. 需求约定 (Requirement Agreement) —— 对应第二空

  • 顾名思义拆解：
  • 约 = 契约 / 互相约束（拉勾）
  • 定 = 拍板定案
  • 连起来记： 客户和开发人员拉勾拍板定下的契约。
  • ☕ Java程序员秒懂：
  • 这就相当于前后端分离开发时的 Swagger API 接口文档。
  • 接口文档一旦定下来，前端（客户）和后端（开发者）就有了约定。前端按接口传参，后端按接口返回。谁也不能耍赖，这就是双方的桥梁。

🚫 避坑指南（为什么不选其他干扰项？）

用大白话帮您排除错误选项，考试时一眼识破陷阱：

  • 需求标准 / 需求管理标准： 带有“标准”二字的，通常是公司级别的规章制度（比如“我们公司规定必须用Word写文档”），它不是针对某个具体项目的文档。
  • 需求用例： 用例（Use Case）只是写需求的一种格式（就像你写代码可以用 if-else 也可以用 switch），它代表不了整个项目的底线。
  • 需求分析： 这是一个动作/过程（大家在会议室头脑风暴），而题目问的是评审后的最终文档（产出物）。
  • 需求变更： 这是基线确定之后发生的事情（改Bug/加新功能），不能用来填补基线本身的定义。

🧠 二、 顾名思义 & 场景记忆法（专为Java开发者打造）

我们用“顾名思义”来拆解题目中的选项。只要看到词语的意思，就能判断它是“生孩子（开发）”还是“养孩子（管理）”。

❌ 为什么 B、C、D 是错的？（属于“需求开发”）

  • 需求获取：顾名思义，就是“获取”信息。客户脑子里有个想法，你去跟他聊天，把想法掏出来。东西还没成型，这属于从无到有的“开发”。
  • 需求建模：顾名思义，就是建个“模型”。就像你写Java代码前，先画个流程图或者数据库ER图。这是在梳理逻辑，属于“开发”。
  • 需求评审：顾名思义，就是大家坐在一起“评判和审查”。需求写完了，产品经理、开发、测试坐在一起开会，说“这个需求没问题，就按这个做”。这标志着“开发”阶段的结束。

> 破题秒杀技巧：只要选项里有“获取”、“建模”、“评审”，说明需求还在“娘胎”里或者刚出生，绝对不属于“管理”！直接排除 B、C、D！

✅ 为什么 A 是对的？（属于“需求管理”）

既然叫“管理”，说明需求已经定下来了，接下来的日子里我们要管好它。想想你平时怎么用 Git 和 禅道/Jira 的：

  1. 变更控制：顾名思义，控制它的改变。
  • 大白话解释：客户突然说“我要加个功能”或者“我要改个颜色”。你不能直接改代码，得走个流程，领导同意了才能改。这就是变更控制。
  1. 版本控制：顾名思义，给它打上版本号。
  • 大白话解释：就像你用 Git 打 Tag（v1.0.0, v1.0.1）。需求文档也一样，今天改一版叫 V1.0，明天改一版叫 V2.0，防止搞混。
  1. 需求跟踪：顾名思义，跟在后面追踪。
  • 大白话解释：顺藤摸瓜。客户提了“登录功能”，你要去追踪：这个功能有没有对应的Java接口？有没有对应的测试用例？确保没有漏写代码。
  1. 需求状态跟踪：顾名思义，追踪它现在的状态。
  • 大白话解释：就像你看禅道/Jira上的任务看板。这个需求现在是“未开始”、“开发中（写SpringBoot代码中）”、还是“已测试完毕”？

对于《需求工程》这个知识点，您不需要去背诵长篇大论的定义，只需要达到以下“条件反射”的程度即可应对高级架构师的综合知识选择题：

  1. 看到“获取、分析、建模、定义、评审” ➡️ 脑子里立刻弹出：这是【需求开发】（前期工作，从无到有）。
  2. 看到“变更、版本、跟踪、状态” ➡️ 脑子里立刻弹出：这是【需求管理】（后期工作，维护已有）。
  3. 做题策略：考题通常是“混搭”的（就像这道真题）。找茬即可，问“管理”就去选项里把带有“获取/建模”的排除掉，剩下的就是正确答案。

子题1

官方解析

本题考察的是需求管理中的需求跟踪概念。

A选项 需求描述：主要是对需求进行文字化、结构化的表达，不涉及与其他系统元素的联系文档，错误。

B选项 需求分析：用于分析和澄清需求，确定需求的优先级和可行性，不是直接建立需求与系统元素的映射关系，错误。

C选项 需求获取：通过访谈、问卷、观察等方式收集用户需求，不涉及与系统元素的联系文档，错误。

D选项 需求跟踪：通过建立需求与其他系统元素（需求、架构、设计、代码、测试、文档等）的依赖关系来确保需求得到正确实现和验证，通常使用需求跟踪矩阵来完成，正确。

🧠 核心记忆法：顾名思义 & Java开发场景代入

这道题的核心是区分需求工程的四个阶段。我们直接从字面意思和您的日常开发来拆解：

🎯 正确答案：D. 需求跟踪 (Requirement Traceability)

  • 顾名思义：“跟” = 跟着，“踪” = 踪迹/脚印。顺着脚印找东西。
  • Java秒懂：这就像微服务里的 TraceId（全链路追踪ID）！
  • 一个请求（需求）进来了，你要看它经过了哪个Controller（架构）、哪个Service（设计）、哪行Java代码（源代码）、有没有报错（测试）。
  • 把这些环节串起来的“联系文档”，就是需求跟踪。
  • 题干触发词：看到“联系文档”、“每个需求与...源代码、测试...之间的联系” ➡️ 脑子里立刻浮现顺藤摸瓜找Bug的过程 ➡️ 选跟踪！

🚫 错误选项的“顾名思义”排雷：

  • A. 需求描述
  • 顾名思义：“描” = 写下来，“述” = 说清楚。
  • 大白话：产品经理把脑子里的想法，写成了一份Word文档（PRD）。它只是写字，不涉及和你的Java代码产生联系。
  • B. 需求分析
  • 顾名思义：“分” = 拆解，“析” = 剖析/判断。
  • 大白话：开需求评审会！大家一起吵架，判断这个需求能不能做？先做哪个后做哪个？（确定优先级和可行性）。
  • C. 需求获取
  • 顾名思义：“获” = 拿到，“取” = 拿来。
  • 大白话：去客户现场开会、发问卷，把客户想要什么给“拿”回来。这是最开始的一步。
